# Architecture

## App shape

**Revision note (post-Milestone 4):** originally PySide6 provided both UI and logic in one process. As of the pywebview switch (see `docs/TECH_STACK.md`), the process split is: Python owns the application process, PDF rendering, voice recognition, and file I/O; an embedded native webview (not a separate app) renders the HTML/CSS/JS frontend inside that same process. The webview loads the pages from a small loopback-only file server that the same process runs (`shared/frontend_server.py`, on a fresh port each launch; it also stamps the saved theme into each page), and the bridge itself is the webview's in-process messaging, not HTTP. This is still a single shipped desktop application — there is no client/server deployment, no network boundary between the two halves — but the UI and application-logic code now live in genuinely separate languages/folders and communicate over an explicit bridge, which the folder layout below reflects.

## Structural pattern: feature-based

Code is organized by feature, not by technical layer (no repo-wide `models/`, `views/`, `controllers/` split), and this still holds on both sides of the Python/frontend split. Each feature folder owns its own view code, logic, and local state. Shared code is promoted to `shared/` only once a second feature needs it — not preemptively.

Two pieces of shared code are justified from the start rather than waiting for a "second use," because they're app-wide by definition, not feature-specific: theme tokens (`docs/DESIGN_SYSTEM.md` is inherently cross-cutting) and icon assets (used in every feature's toolbar/nav). Under pywebview, `frontend/shared/theme.css` (the CSS custom properties the HTML uses) is the *only* place token values live — no other frontend file may contain a literal colour. Python code that needs a colour (the native title bar in `shared/window_chrome.py`, the app-icon build script) reads it from that file through `shared/theme.py`'s `token(theme, name)` rather than keeping a second copy that could drift; the Python-side colour dictionaries that used to live in `theme.py` were removed for that reason.

## Why `src/lector/` and not a flat `lector/` at root

Standard Python packaging practice (the "src layout"): it prevents accidentally importing the in-development package via the current working directory instead of the installed one, which is a common and confusing bug in flat layouts. Worth the one extra directory level.

## Feature boundaries

- **`voice/`** owns speech recognition and command interpretation. It does not know about rendering or DOM structure — it emits recognized intents (e.g. `NEXT_PAGE`, `HIGHLIGHT("some phrase")`) across the bridge to the frontend, which decides what to do with them. This keeps the offline speech engine swappable later without touching UI code.
- **`annotations/`** owns both the fuzzy speech-to-text matching logic *and* the PyMuPDF write layer, because they're tightly coupled (match result directly becomes the annotation's coordinates) — splitting them into separate features would add indirection without a real benefit. The save-confirmation dialog itself is a `frontend/` concern (it's UI); `annotations/` only handles the write once the frontend confirms the choice. The *string-level* edit-distance primitive it matches with lives one feature over, in `voice/fuzzy.py`, because Milestone 6's navigation grammar needed the same arithmetic first and two copies would inevitably drift apart. That is a shared utility, not a shift in ownership: `annotations/` still owns the matching *logic* — which words are candidates, scoping to the visible viewport, breaking ties by reading order, and choosing the span to write.
- **`reading/`** (Python side) owns page rendering and what "current viewport text" means for each layout, expressed as bounding-box data sent to the frontend — this is what `annotations/` depends on to know what's matchable at any given moment. The frontend (`frontend/pages/reading.html` + its JS) owns which layout (book/strip) is visually active and renders the bounding-box overlays it's given; per the open question flagged during design, this split must still behave consistently regardless of active layout.
- **Pointer hit-testing lives on the frontend, word geometry and the write do not.** Deciding which word sits under the cursor has to be answered on every `mousemove` to keep the selection wash attached to the pointer, which is far more often than is sensible to cross the bridge for. So `api.get_page_words()` hands the frontend a page's word boxes once (in PDF points, so zoom never invalidates them — the "bounding-box data sent to the frontend" above), the frontend resolves cursor → word locally while the drag is live, and `api.highlight_words()` takes back the *word index range* it had drawn. Indices rather than coordinates on purpose: the annotation that gets written is then by construction the run the reader saw selected, instead of the result of a second, independent hit-test that could disagree with the preview. The two ends of a drag are resolved by different rules on purpose — the anchor by containment (`wordIndexAt`), so a press on empty page starts nothing, and the moving end by proximity (`nearestWordIndex`), so a drag can run past the end of a line without stopping. Composing the shape stays duplicated in both places (`highlighter.merge_line_rects` and `mergeLineBoxes` in `reading.js`), and the two are required to agree — each carries a comment pointing at the other.
- **Boxes cross the bridge on the page as shown, not as MuPDF reports them.** MuPDF gives text, search hits and highlight quads on the *unrotated* page, and highlights are written there, but it renders a page turned by its /Rotate, and `page_size_points` is that turned size. So every box the reading view lays over the page image (`get_page_chars`, `get_page_highlights`, `find_in_document`'s hits) goes through `PdfDocument.as_shown` (or `search._shown_box`) on its way out, and the voice viewport's `y0`/`y1`, which the page measures on the image, are matched against `PdfDocument.words_as_shown`. Nothing comes back as coordinates: a highlight returns as character or word indices, which are the same in either space. A page with no rotation is unchanged. Before hardening H6 the boxes went out unrotated, so on a page turned 90° a drag selected the wrong words and find marks landed on blank paper. On a sideways page a line of text runs down the screen, and the frontend's "nearest character on the line it's level with" rule for a drag that leaves the text still assumes lines run across.
- **Highlight colours: one palette, read from `theme.css` by both sides.** The five names live in `shared/theme.py` (`HIGHLIGHT_COLOR_NAMES`); their values are `theme.css`'s theme-independent `--highlight-<name>` tokens, which the frontend uses for swatches and `highlighter.py` reads (`theme.shared_token`) for the PDF's `/C` and appearance stream. Only names cross the bridge. The active colour is a setting (`settings/store.py`'s `highlight_color`), so `api.highlight_chars` and `api.highlight_by_voice` read it rather than being told; a voice one-off passes its own colour and leaves the setting alone. **Edits to existing highlights** go through `PdfDocument`: `set_highlight_color` and `remove_highlight` name a highlight by its annotation xref (what `api.get_page_highlights` hands the frontend). The undo stack holds one `_Edit` per change — a highlight's colour going from `before` to `after`, `None` meaning absent — so add, recolour and remove are one mechanism and undo/redo are the same move in opposite directions. Edits refer to their annotation through a shared, mutable `_HighlightRef`, because an undone removal re-creates the annotation under a new xref and every later edit to it must follow; colours are stored as raw RGB so another app's highlight, recoloured or removed and then undone, comes back in its own colour (and with its note and author). **On the frontend**, `frontend/pages/highlight-colors.js` lays a transparent `<button>` over every highlight on a visible page — what makes each one clickable, tabbable and named for a screen reader — and owns the swatches, the targets and the editor (recolour, opacity, thickness, remove), while `highlight-options.js` owns the rail's split highlight tool and its two cards; `reading.js` hands it the visible page elements and refreshes the page after a change, the same `configure…()` split `find-bar.js` uses.
- **Freehand strokes are a second kind of highlight: one `/Ink` annotation each.** `highlighter.py` describes a highlight's shape as a `TextShape` (a `/Highlight`'s per-line boxes) or an `InkShape` (strokes, width, opacity, blend mode); `HIGHLIGHT_TYPES` is both annotation types, and every place that lists, counts, loads, verifies a save or guards undo history (`highlight_annots`, `highlight_count`, `_load_highlight`, `_verify_saved`, `_forget_history_if_stale`) goes through it, so a stroke is counted, marked on the progress bar, recoloured, removed, undone and kept through an overwrite like a text highlight. `add_ink` sets `/C`, `/BS` width (`INK_WIDTH_PT`, 14), `/CA` (`INK_OPACITY`, 0.6) and `/BM` Multiply before `update()`, so MuPDF's generated appearance carries them (with round caps and joins); recolouring ink only changes `/C` and regenerates it. The undo stack's `_Edit` now goes from one `_Look` (colour and shape) to another, so add, remove and recolour are as before and a change of shape — an ink stroke straightened on release — is the same move: delete and write again under a new xref, through the shared `_HighlightRef`. A `_Look` holds the drawing as the PDF has it (`shape_of(annot, bounded=False)`), so an undone removal of another app's ink writes back every stroke; the bounded copy (`bounded=True`: on the page, at most `INK_MAX_STROKES` / `INK_MAX_STROKE_POINTS`) is only what `highlights_on_page` lists, and `highlight_count` counts exactly what it lists. `api.add_ink_stroke(page, points, straightened)` takes the stroke as drawn and, if the frontend straightened it, the line's two ends; `PdfDocument.add_ink_stroke` records the drawn stroke and then the straightening as two edits, so the first Undo gives back the drawn stroke. Points cross the bridge on the page as shown (like every box) and are taken back with `page.derotation_matrix` (`_from_shown`), clamped to the page; `shown_strokes` turns them round again for `get_page_highlights`, whose ink entries carry `kind: "ink"`, `strokes`, `width` and, as their one rect, the box the stroke paints (`ink_bounds`). The bridge refuses anything but finite `[x, y]` pairs, at most `MAX_INK_POINTS` (4096), before any of it reaches the PDF. **On the frontend**, `freehand.js` decides each press (`pressHighlightTool`): Alt, or a press not on text, is a stroke; on text, `reading.js`'s selection. A text layer's boxes are its glyphs', but OCR finds "characters" in pictures (a one-letter box as wide as a photo, a real line stretched down through a barcode), so on an OCR page `isPointOnText` only counts a box shaped like a glyph (≤ 3× the page's median character height, ≤ 2.5× as wide as tall). A page whose OCR has not run yet is a text press, which reads it. A press before the page's characters have arrived is held as a stroke that draws nothing until they come, then goes whichever way they say (handing the press, its moves and its release to the selection if it was on text). The live stroke is kept as fractions of the page image and drawn in `#inkLayer` as one SVG path whose viewBox is the page in points (so 14pt is the same on paper at any zoom), the SVG at the ink opacity and the layer multiplied onto the page (`mix-blend-mode` on `#inkLayer`, not the SVG: the layer's z-index makes it a stacking context, which a blend inside it cannot see out of), which is how the PDF draws it and why a stroke crossing itself does not double up. `ink-geometry.js` (pure, tested under Node) simplifies, smooths, decides straightening and snaps to the axes; the bridge sees one call per stroke, never the per-frame points. The preview is removed only once the commit's re-rendered page image is on screen. `highlight-colors.js` gives each drawing a target whose SVG path is what takes the pointer, and `highlightAtPoint` hit-tests drawings by distance to their path.
- **`api.py`** is the only file that both sides import against — it's the contract. Frontend JS never reaches into `features/` directly, and Python features never touch `frontend/` files; everything crosses through `api.py`'s exposed methods and its corresponding `bridge.js` wrapper.

- **Find in document is sliced in Python and drawn in JS.** `features/reading/search.py` runs PyMuPDF's `search_for` page by page and stops after 50ms (`SLICE_BUDGET_S`), returning that slice's hits in PDF points plus the page to resume from; `api.find_in_document(query, start_page, end_page)` is one slice. A whole-document scan in one bridge call would hold up the page renders queued behind it, so `frontend/pages/find-bar.js` asks for slices in a loop instead, from the page being read to the end and then from the start back to it. Cancelling is not a backend call: each search carries a generation number, and a slice that returns for an older one is dropped and not followed up, which also makes out-of-order replies harmless. `search_for` gives one rect per line of a hit, so `group_fragments` rejoins a hit that wraps lines (by checking the text inside each rect spells out the query), and a slice counts the pages that have any text so the frontend can tell a scanned PDF from a missing word. Marks are drawn the way the selection wash is: an overlay over the page area, positioned from each page image's measured rect, repainted on scroll, zoom preview and refresh, and handed page geometry by `reading.js` through `configureFindBar()` so `find-bar.js` never needs to know which layout is showing. This is separate from voice highlight matching, which stays scoped to the visible viewport (`docs/PRD.md`).
- **Highlight options: three text styles, opacity per style, a freehand width.** `shared/highlight_options.py` holds the styles (highlight, underline, strikethrough), the opacity range, defaults (60 / 100 / 100%) and snap, and the width presets (4–36pt, default 14); `settings/store.py` (`highlight_style`, `highlight_opacity`, `ink_width`, each validated on read), `highlighter.py`, `api.py` and the frontend (through `api.get_highlight_options`) all read it. A `TextShape` carries its style and opacity: `add_text_markup` writes a `/Highlight`, `/Underline` or `/StrikeOut` with `/C` and `/CA` and rewrites the appearance (a box per line, or a bar per line placed by `line_metrics` from the page's characters — a text layer's baselines and sizes, which `chars_on_page` now reads from `rawdict`, or OCR boxes), keeping the ExtGState MuPDF generated for the opacity and, for a highlight, Multiply. `HIGHLIGHT_TYPES` gained the two line types, so counting, the progress bar's markers, listing, removal, undo and save guards treat them as highlights with no change of their own. `PdfDocument` passes the page's characters wherever a line is written (add, recolour, undo of a removal: `_chars_for`). **Restyling in place:** `restyle_highlight` changes colour, opacity and an ink stroke's width on the same annotation (same xref); `_move_highlight` uses it whenever two looks share their geometry (`same_geometry`), and only re-adds for an add, a removal or a change of shape. `set_highlight_appearance(page, xref, opacity, width, gesture)` is the editor's: every change one gesture makes (a slider drag sends a value per step) is one undo step — the top `_Edit` is replaced by one from the gesture's first look to its latest (never mutated), and dropped when the gesture ends where it began. Freehand strokes take the reader's width and the Highlight opacity at the bridge (`api.add_ink_stroke`). **On the frontend**, `highlight-options.js` owns the split tool — the style badge and style card, the preview button and settings card, one open at a time — and the active colour and style (moved from `highlight-colors.js`, which keeps the swatches, targets and editor), and builds the opacity and thickness controls both the settings card and the editor use. It does not hold the tool's on/off state: `reading.js` hands it `isOn`/`setOn` through `configureHighlightTool()`, and its page-level keydown passes H, U and S to `pressHighlightStyleKey` after the shared typing and dialog guards (`isTypingTarget`, `dialogOpenAtKey`) and only without modifiers; `range-slider.js` is the slider behaviour the zoom popover and both opacity sliders share (drag state, snap only while dragging, double-click-the-thumb reset, ticks). An opacity change waiting to be written goes before any other option is set, since each setter's reply carries every stored option. Voice: `command_grammar`'s `UNDERLINE`/`STRIKETHROUGH` (and `_SENTENCE`) triggers sit in the same `_HIGHLIGHT_TRIGGERS` list as highlight's, each style's sentence form before its plain one; a sentence trigger needs the word "sentence" heard, since "strike through the quick" scores 0.74 against "strike through the sentence". `api.highlight_by_voice` takes the command's style. The tool's settings by voice need no new endpoint: `SET_OPACITY` ("opacity <n>", parsed with an exact lead and only the slider's tick values, `OPACITY_VALUES`), `THICKER`/`THINNER` and `HIGHLIGHT_MODE`/`UNDERLINE_MODE`/`STRIKETHROUGH_MODE` are fixed phrases or a number the frontend acts on through the same setters the cards use; a "… mode" phrase only matches when the word "mode" was heard (`_fixed_phrases`), since "highlight more" scores 0.93 against "highlight mode" and is a highlight of "more".
- **Scanned pages are read on demand, one page at a time, in a worker process.** A page with no extractable text that shows an image is "scanned" (`features/reading/ocr.py`'s `page_needs_ocr`); detection is per page, because a PDF can mix scanned pages with ordinary ones. Nothing is read when a file opens. A page is read when the reader presses on it with the highlight tool, when a voice highlight over it comes up empty, or — with voice on — once it has stayed on screen, unscrolled, for one second (`reading.js`'s dwell prefetch: visible pages only, one at a time). OCR produces the same `Char`/`Word` lists as a text layer, and `PdfDocument.chars_on_page`/`words_on_page` hand them out in its place, so selection, speech-to-match, `merge_line_rects` and the annotation writer are unchanged; highlights land in the PDF as ordinary highlight annotations, and no text layer is ever written into it. The engine is the Tesseract compiled into PyMuPDF, run on a single-page, annotation-free copy of the page. Real scans need two corrections first, both measured on a speckled, slightly crooked 1998 office scan where the first version lost 45% of a memo: the page is straightened (`detect_skew`, a numpy projection-profile search up to ±10°; MuPDF's own detector read 1.1°/2.9°/3.8° for tilts of 2°/4°/7°), by rendering it turned rather than turning a bitmap, so word boxes map back exactly through the inverse render matrix; and isolated black specks are removed (`despeckle`), because on a noisy page Tesseract's layout analysis drops whole clear lines. Then up to three reads — as rendered at 300 dpi, despeckled, despeckled at 200 dpi — stopping at the first that puts 90% of the page's ink inside recognized words (`ink_coverage`; Tesseract reports no confidence through MuPDF, but text it skipped is still ink). Clean pages stop after the first read, unchanged from before; the office scan went from 55% to 91% of its words, and the same page tilted 7° from 5% to 70%. A median filter was tried and rejected: it blanked one clean page entirely. It runs in a separate process (`multiprocessing`, spawn, one worker, started on first use) because PyMuPDF holds the GIL for the whole call — measured at 1.3 s of a 1.9 s page with the main thread stalled — which in a thread would freeze every bridge call; the process also contains a Tesseract crash, and a job that passes 120 s is failed and its worker replaced. Results go to `%APPDATA%\Lector\ocr\` (beside settings.json; `ocr_cache.py`) as JSON, keyed by a hash of what the page draws — its content stream, its images (raw bytes for JPEG/JPEG 2000/JBIG2/CCITT, decoded bytes otherwise, since saving with deflate recompresses a plain stream), rotation, page box, language, resolution and `OCR_PIPELINE_VERSION`, bumped when pages are read differently so older results are re-read — so a page keeps its text through highlighting, Save a copy and overwriting. The folder is capped at 100 MB, least recently used first. `is_readable` turns noise into "no text found" rather than gibberish to match against: below 12% common English words and plain numbers, counting only numbers and words of three letters or more, since noise is full of chance "a"/"be"/"of" (measured: real scanned pages 17–43%, a blurred, skewed phone photo 7%). OCR can still miss part of a page that was otherwise read (a large bold heading, a line on a crooked noisy page); a press there is not on text, so it draws a freehand stroke (see "Freehand strokes" below) rather than highlighting. Highlights on a straightened page are upright rectangles around slanted text, so on a tilted scan they spill onto the neighbouring line; drawing them as slanted quads is not done yet. The bridge reports status per page (`get_page_chars`'s `ocr`: null, "needed", "running", "done", "no_text", "unavailable", "error"), `ocr_page` starts a read, and a `lector:ocr` page event reports the outcome. Voice has one extra case: a recognizer can only hear words that were in its vocabulary when it was built, so "highlight <words>" over an unread page arrives as a bare "highlight" (`command_grammar.is_bare_highlight`); that, or an empty match, carries the page's OCR status so the mic pill says "Reading text on this page…" and then "Text read — say it again" instead of "not a command I know". Find in document does not use OCR text (out of scope for now).
- **Home lists first and draws thumbnails after.** Measured on a cold 20-file Recent list, rendering first-page thumbnails was about 83% of the list's backend time (opening each PDF for its page count and title was the rest). So `features/home/recent.py` keeps two mtime-keyed caches: `list_recent()`/`list_favorites()` open each file for its count and title only, and hand back a thumbnail only if one is already rendered, marking the rest `thumbnail_pending`; `api.get_thumbnails(paths)` renders those, four per call, for listed paths only (a round trip per thumbnail cost several times the render itself). PyMuPDF is used from separate bridge threads, so `recent.py` serialises its document work behind one lock. On the page, `frontend/pages/library-loading.js` holds the loading placeholders: a whole-list skeleton chosen from the grid/list view and last known file count that the page server writes into `<html>` (`recent.page_state()` → `frontend_server.with_page_state()`), so no bridge call stands between the page and the skeleton's shape. It appears only after 150ms, stays at least 300ms, and fades out over the rows drawn under it. Each pending thumbnail slot also gets a placeholder, until its batch arrives. `home.js` asks for the list at the very start of `init()`, alongside the first-run check, rather than after the icons and voice set-up, which used to hold it back by 200-250ms. A load overtaken by a newer one (Recent, then Favorites) draws nothing.

- **The reader's left edge: progress bar and outline panel, both fed by the state the reader already has.** `features/reading/outline.py` turns PyMuPDF's `get_toc()` into a nested tree (`outline_tree`; an entry pointing nowhere keeps `page_index: None`) and the top-level chapters (`chapter_segments`: one per top-level entry, in page order, together covering every page, an untitled leading one for pages before the first chapter), which the progress bar uses only to name the chapter in its tip and its spoken value; the bar itself is drawn by page. `api.get_outline()` returns both; `api.get_page_thumbnail(index, width)` renders a page at a fixed pixel width whatever the zoom (clamped 16–480px) for the Pages tab and the bar's hover preview. The bar's highlight markers need no call of their own: `_state()` carries `highlighted_pages` (every page with a highlight in the open document, saved or not), so the markers follow every add, recolour, removal, undo and redo through the replies the reader already receives. On the frontend, `progress-bar.js` and `outline-panel.js` follow `find-bar.js`'s `configure…()` split: `reading.js` owns navigation and hands them `jumpTo(index)`, and calls `updateProgressBar(state)` / `updateOutlinePanel(state)` from `updateChrome()`, which every page and highlight change (strip scrolling included) already passes through. `goNext`/`goPrev`/`goToPage` call `flashProgressBar()` when the page changed, so a page change by keyboard, voice, toolbar or outline briefly widens the bar; strip scrolling does not. Whether the bar is active or idle is `progress-bar.js`'s own: `updateProgressBar` wakes it on a page change, its own listeners on hover, focus and a pointer near the left edge, and `reading.js` calls `wakeProgressBar()` from the book and strip scrollers' scroll events; a timer idles it 3s later. The bar's geometry (pitch, gap, pill or continuous mode, marker boxes, where the fill ends) is pure functions in `progress-layout.js`, loaded before `progress-bar.js` and tested under Node; `progress-bar.js` measures the track (a `ResizeObserver`) and draws from it. Where the read fill ends comes from `reading.js` (`currentPageReadFraction()`, a `{ page, fraction }`) and is passed to `updateProgressScroll()` from `updateChrome()`, the scrollers' scroll events (once a frame) and the page-area `ResizeObserver` (a resize or zoom changes the scroll range). In Strip it is `progress-layout.js`'s `progressReadPosition()`: the overall progress `scrollTop / (scrollHeight − clientHeight)` places a reading line between the view's top and bottom, so the end of the scroll is exactly 100%; in Book it is the current page and how far down it is scrolled, the last page always full. The fill's page is kept apart from the bar's current page (`progressFillPage`), since at the end of the strip the line is on the last page while the page being read, by the view's top, is an earlier one. A `ResizeObserver` on the page area repaints highlight targets and find marks when the panel opens or closes, since that resizes the page without a window resize. "show outline"/"show pages" put the panel's entries under the numbered-overlay picker by pushing the existing `picker` context (`createVoiceScope("picker")`), so a bare number resolves to `router.PICK` and `outline-panel.js` turns it into a page (outline entries: in the order shown; thumbnails: the page number itself). The panel's width is `--outline-width` on the panel, set by `outline-panel.js` from a pointer drag on `#outlineResizer` (pointer capture) or its arrow keys, clamped to 168–400; the end of a resize calls `api.set_outline_width`. Thumbnails are a CSS grid of 128px columns (`repeat(auto-fill, 128px)`), rendered at 128 × devicePixelRatio, so a resize changes their layout, not their bitmaps; `redrawPageThumbsForPixelRatio()` re-queues ones whose `data-rendered-width` no longer matches when `reading.js`'s pixel-ratio watch fires. While the panel is open the progress bar never widens: `configureProgressBar` gets `panelOpen()` (`isOutlinePanelOpen`) and `preview(index)` (`previewOutlinePage`), and `expandProgress()` returns early when the panel is open; its pointer handlers call `preview` instead of showing the tip. `previewOutlinePage` puts `.is-previewed` on the thumbnail (Pages) or on the row of `shownOutlineItem(currentOutlineItem(index))` (Outline) and scrolls it into view with `scrollElementTo` only when it is not wholly visible. `configureOutlinePanel`'s `onToggle(open)` calls `progressPanelToggled`, which narrows a widened bar on opening and clears the preview on closing. Settings: `default_view` (book/strip, the layout `open_pdf` starts a PDF in before any saved position is restored), `progress_bar` (bool, default on), `outline_panel_open` (bool) and `outline_panel_width` (int, 200, clamped) in settings.json, through `api.get_reading_preferences` / `set_default_view` / `set_progress_bar` / `set_outline_open` / `set_outline_width`.
- **Focus mode and page centring are frontend-only, and nothing about them is stored.** `frontend/pages/focus-mode.js` toggles two classes on `.reading-view`: `.is-focus-fading` (every `.focus-chrome` element, the topbar, rail, footer and their dividers, fades to 0) and, one `--dur-fast` later, `.is-focus-mode` (they leave the layout). It is handed the active scroller through `configureFocusMode()`, the same `configure…()` split as `find-bar.js`, and moves its `scrollTop` by however far the scroller's top moved, so the text being read stays put. Its state lives in a module variable only: the reader page is loaded afresh for every PDF, so every PDF opens with it off. The same file owns the topbar's Focus mode button (icon, `.active`, `aria-pressed` and tooltip follow the state), the 3s toast on entry (its dismiss function kept, so leaving early takes it back), and the header-on-demand: a document `pointermove` listener sets `.is-focus-peek` when the pointer is within 8px of the top, and clears it 300ms after the pointer has left the topbar, unless `configureFocusMode()`'s `holdsPeek()` hook (the zoom slider open) says to wait; `reading.js` calls `settleFocusPeek()` when the slider closes. In CSS the topbar stays `display: flex` in Focus mode, `position: fixed` and translated above the window, so it slides in over the page without moving it. Esc's order lives in `reading.js`'s keydown handler: the zoom slider is checked before the guard that skips keys typed into inputs (the slider is one), and Focus mode is the last branch. The voice side is two fixed phrases in `command_grammar.PHRASES` (`FOCUS_MODE`, `EXIT_FOCUS_MODE`), so they are heard in the `reading` context only; `reading.js`'s `renderMicState` passes every mic state to `showFocusVoice()`, which shows a floating copy of the mic pill while the state is "listening". `frontend/pages/page-centering.js` is a pure `pageOffsetForWindow()` plus `centerPageOnWindow(scroller, page)`, which writes `--page-offset` on the scroller; `reading.js` calls it from the page-area `ResizeObserver`, which also observes the page card and the strip column, so a zoom, a layout switch, the outline panel or Focus mode re-centres the page and repaints what is drawn over it.
- **100% is real size, and the page box and its bitmap are sized separately.** `PdfDocument` scales by `zoom × CSS_PX_PER_POINT` (96/72): `page_sizes()` and `page_css_size()` are the page's CSS size, rounded up as PyMuPDF sizes a pixmap so at a pixel ratio of 1 the bitmap is exactly the box; `render_page(index, device_scale)` draws the bitmap at that times the web view's `devicePixelRatio` (clamped 1–4), held under `MAX_RENDER_PIXELS` (16M) by drawing fewer pixels for the browser to scale up. `api.get_page_image(index, device_scale)` returns the bitmap with the CSS size as `width`/`height`, which `reading.js` puts on the `<img>` as attributes (what `applyZoomPreview()` scales from). Everything drawn over a page (highlight targets, the selection wash, find marks, the voice viewport) and click-to-text already took its scale from the page element's measured width over its size in points (`pageScale()`), so none of it changed. `reading.js` re-renders when `devicePixelRatio` changes (a `matchMedia` resolution query). A stored zoom keeps its number, so a PDF left at 100% reopens a third larger than before.
- **Zoom modes live on the frontend; the backend only ever holds a percentage.** `frontend/pages/zoom-fit.js` is pure arithmetic (the slider's logarithmic mapping, tick places, the snap to 100%, `fitZoom()`, the value's text), run under Node by `tests/test_zoom_control.py`. `frontend/pages/zoom-control.js` owns the popover, its ticks, the drag state (only a pointer drag snaps) and the mode (`null`, Fit width or Fit page; a module variable, never stored), and gets the zooming itself from `reading.js` through `configureZoomControl({ setZoomPct, fitGeometry, onClose })`, the same `configure…()` split as `find-bar.js`. `fitGeometry()` is the page area's size and the current page's size in PDF points from `api.get_page_size_points(index)`, cached per page. `fitZoom()` leaves 24px a side, converts with 96/72, and rounds down to 0.01% a pixel short, so the rounded-up page box can never scroll; `PdfDocument.set_zoom` keeps four decimals (`ZOOM_DECIMALS`) for that, while `zoom_pct` stays whole for display. The fit goes to the backend as an ordinary `set_zoom`, which is what Resume reading then remembers. `refitZoom()` runs from a `ResizeObserver` on the page area (at most once a frame) and after `toggleLayout()`; every other way of zooming calls `leaveZoomFit()` first. `setZoomPct()` keeps one `set_zoom` on the bridge at a time and sends only the latest percentage asked for, since pywebview answers each call on its own thread and a slider drag or a window being dragged asks for one a frame; a reply with a newer percentage already queued is not drawn. `PdfDocument.MIN_ZOOM` is 0.25. The voice side is three phrases in `command_grammar.PHRASES` (`FIT_WIDTH`, `FIT_PAGE`, `ACTUAL_SIZE`), so reader-only, and a "zoom" section in `reference.py`.

## App-close gatekeeper (Milestone 8.1)

*`Api.handle_window_closing`, bound to `window.events.closing` in `__main__.py`.*

pywebview's `window.events.closing` is registered with `should_lock=True` (see `webview/window.py`), which means every handler on it runs **synchronously, on the platform's own UI thread** — on Windows, inside WinForms' `FormClosing` — before the window is allowed to close, and a handler that returns a literal `False` cancels the close. That is a problem for a dirty-document check, because the only existing "ask the reader what to do" UI is `promptSaveIfDirty()`, an async JS function that opens a dialog and awaits its result — and blocking the UI thread until it resolves risks deadlocking against the very message loop `window.evaluate_js()`'s promise-callback delivery depends on.

The gatekeeper avoids that by never blocking: on a dirty document, it returns `False` to cancel the *first* close attempt, fires `promptSaveIfDirty(true)` via `window.evaluate_js()` with an async callback, and — only once that resolves to "yes, close" — sets a `_closing_confirmed` flag and calls `window.destroy()` to reissue the close. `window.destroy()` is safe to call from the callback's own (non-UI) thread because pywebview already marshals it back to the UI thread itself (`platforms/winforms.py`'s `destroy_window` wraps it in `Control.Invoke`). `_closing_confirmed` exists so that reissued close doesn't re-run the same check and prompt a second time. A clean document, or no document open, closes immediately — the check only ever adds a step when there is something to lose.

## Voice context router (Milestone 8.1–8.12)

*Extends the reading-only voice grammar to cover the whole app.*

The recognizer has always run one active grammar at a time — `wake.py` already proves this pattern by swapping between a minimal idle grammar (the wake phrase only) and the full command grammar on activation, and `api.py`'s `update_voice_viewport()`/`_viewport_vocabulary()` already proves the grammar can be widened dynamically (the visible page's own words, during highlighting). Full in-app voice control generalizes both: instead of exactly two grammars (idle / reading-command), a router tracks whichever screen or dialog currently has focus (`home`, `reading`, `settings`, `save_dialog`, `open_dialog`, `picker`, `dictation`, extendable) and sets the active grammar to a fixed set of **global** commands (available regardless of context — "undo", "redo", "help", "go home", "close app") unioned with that context's own scoped command set. `command_grammar.py`'s existing reading-view grammar becomes the `reading` context's scoped set without changing its behavior; Home and Settings gain their own.

Two new UI patterns fall out of this, both frontend-only (no new architectural boundary):
- **Numbered-overlay picker** — for a list item with no natural single-word voice label (a specific Recent card), an overlay badges each item with a number under a `picker` context; saying the number performs the same action a click would.
- **Dictation mode** — for the one free-text field that exists today (the command-reference panel's search field), a `dictation` context temporarily runs Vosk open-vocabulary rather than grammar-constrained, the same generalization of `update_voice_viewport()`'s existing widening trick, scoped narrowly rather than left on globally.

The native Open/Save-As file dialogs (`api.py`'s `open_pdf_dialog()`, the "Save a copy" path) are replaced with in-app `open_dialog`/`save_dialog` screens for the same reason `annotations/`'s save-confirmation dialog is already a `frontend/` concern rather than an OS-native one: the router can only see and control the app's own UI, not OS chrome.

**Implemented (Milestone 8.4):** `features/voice/router.py` holds `resolve(context, text, alternatives)` and `vocabulary_for(context)`, and `api.py` holds the context itself (`self._voice_context`, defaulting to `reading` so a caller that never calls the new `set_voice_context()` — every pre-8.4 test and any future one that doesn't need this — keeps behaving as it did before the router existed). Only `home` and `reading` claim a context so far, from `home.js`/`reading.js`'s `init()`; `settings` and the dialog/picker/dictation contexts are named in `router.CONTEXTS` but have no scoped grammar or caller yet, pending 8.5–8.8. The global set built in 8.4 is `undo`/`redo`/`help`/`go home` only — **"close app" is deliberately not among them**, held for 8.11 once 8.1's close gatekeeper (above) is what it needs to invoke, rather than being included here ahead of that dependency existing.

**Implemented (Milestone 8.7):** the native Open/Save-As dialogs described above are gone. `features/dialogs/browser.py` (`list_directory`, `default_open_dir`, `default_save_dir`) is a plain filesystem helper with no pywebview dependency, called from three new `api.py` bridge methods (`browse_directory`, `get_save_dialog_start`, and `perform_save`, whose `path` parameter now comes from the dialog rather than `create_file_dialog()`'s return value). On the frontend, `frontend/js/file-browser.js`'s `createFileBrowser()` factory backs both Home's `open_dialog` and Reading's `save_dialog` screen — one shared implementation rather than two, since the two differ only in whether picking a file closes the dialog immediately (Open) or fills a filename field first (Save). Both reuse 8.6's numbered-overlay badge, but always visible for as long as the dialog is open rather than toggled, since every row in a file listing lacks a natural spoken label the way a Recent card's own filename gives it one. This is the one place voice needs to keep working *while* a `.dialog-scrim` is open, which required narrowing `voice.js`'s push-to-talk-suppression check (originally "any open dialog blocks Space") to exclude scrims carrying a new `.voice-dialog` marker class — the keyboard-only save-confirmation and reference dialogs still suppress push-to-talk unchanged.

**Implemented (Milestone 8.8):** dictation mode, described above, is live for the one free-text field that exists — the command-reference panel's search box. `router.py` gained a `DICTATION` context that is the single exception to "global commands match first": a dedicated branch in `resolve()` checks it before the global table, so a dictated sentence containing a word like "undo" is never misheard as that command — only "done" (`STOP_DICTATION`) and "cancel"/"never mind" (`CANCEL`) resolve to anything there; everything else comes back as `command: None` and is treated as the dictated text itself. `START_DICTATION` ("start search") is a global intent rather than scoped to `reading`, since the panel opens as an overlay without changing the underlying context — mirroring how `HELP` already works, and a silent no-op anywhere that doesn't wire it into an action table. `engine.py`'s `set_vocabulary(None)` now builds the Vosk recognizer with no grammar argument at all (true open-vocabulary), rather than the widened-but-still-constrained word list `update_voice_viewport()` uses; `api.py`'s `_refresh_voice_vocabulary()` special-cases `DICTATION` to call it and skip viewport computation. Only final recognition results are ever written into the field — partial results are not streamed in, since a partial cannot yet be told apart from the start of "done"/"cancel". The context dictation returns to on exit is hardcoded to `reading` rather than tracked as a stack, since the panel is, today, only ever opened from that one screen.

**Implemented (Milestone 8.9):** two more confirmation dialogs become their own router contexts, following the same "the router can only see and control the app's own UI" shape 8.7's dialog contexts already established, rather than either dialog trying to interpret global commands meant for the screen underneath it. `REMOVE_CONFIRM` backs the new remove-from-Recent confirmation (`docs/DESIGN_SYSTEM.md`'s "Remove-from-Recent affordance" section, `docs/PRD.md`'s scoped-in note): `HOME_PHRASES` gains `REMOVE_RECENT`/`REMOVE_PICKER` to open it (directly for the single most-recent entry, or via 8.6's numbered-overlay picker in a removal mode for any other), and the context itself scopes `CONFIRM_REMOVE`/`CANCEL`. `SAVE_CONFIRM` backs the older, separate "Save changes?" dialog (`save-dialog.js`) — a **distinct** context from 8.7's `SAVE_DIALOG`, which already owns that name for the Save-As folder browser's own row-picking grammar; `SAVE_CONFIRM` instead reuses the `SAVE_COPY`/`SAVE_OVERWRITE` intents 8.5 defined for Settings (a spoken copy/overwrite choice both selects and confirms in one command, the same one-command-does-the-whole-action shape `CONFIRM_REMOVE` uses), adding only one new intent, `DONT_SAVE`, gated as a no-op when the dialog's Don't-Save button isn't offered. Both contexts fall through the same generic `_CONTEXT_PHRASE_TABLES` lookup `SETTINGS` already uses in `resolve()` — no new branching was needed in the router's control flow, unlike `DICTATION`'s dedicated branch above.

**Added later (Favorites):** four more `HOME_PHRASES` intents, no new context. `OPEN_FAVORITES`/`SHOW_RECENT` switch Home between its two lists (`home.js`'s `homeSection`); `FAVORITE_RECENT`/`FAVORITE_PICKER` repeat 8.9's most-recent/numbered-picker split for starring, with the picker gaining a third mode, `favorite`, beside `open` and `remove`. Starring toggles and has no confirmation step (unlike removal, saying it again undoes it), so neither intent routes through a dialog context. Storage is `settings.json`'s own `favorites` list (`store.get_favorites`/`add_favorite`/`remove_favorite`), not a field on the recent entries, so a favorite survives Recent's 20-item cap; `Api.get_favorites`/`set_favorite` are the bridge, and `home/recent.py`'s `list_favorites()` shares its entry shape with `list_recent()`.

**Implemented (Milestone 8.10):** `features/voice/reference.py`'s `categories()`/`panel()` — the payload behind the "What can I say?" panel — take a `context` parameter and build different categories for `HOME` and `SETTINGS` from their own `router.HOME_PHRASES`/`SETTINGS_PHRASES` tables, rather than always returning the reading grammar's "Moving around"/"Highlighting"/"The app itself" regardless of which screen asked. `api.py`'s `get_command_reference()` passes its own `self._voice_context` through, so the panel — once a screen wires "help" to open it — shows only what that screen can actually do. Every context without its own categories (`READING`, and every dialog/picker/dictation context, none of which offer a "help" entry point today) keeps the pre-8.10 reading categories as its default, which is also what every existing caller of `categories()`/`panel()` with no argument still gets.

**Superseded (Milestone 8.13):** the "What can I say?" list is one shared component (`frontend/pages/command-reference.js` + `frontend/shared/reference.css`, markup and styles defined once, loaded by Home, Settings and the reader) driven only by `features/voice/reference.py`, which builds it from every router and grammar table. `panel(context)` now returns `sections` (not `categories`) and each command's `phrases` (every phrasing the recognizer accepts, not a sample); a phrase with a variable is a pattern (`{page}`, `{number}`, `{words}`) that the page fills with the real range through `configureCommandReference()`. Every screen gets every section: `context` decides only which come first (that screen's own, then the rest in one fixed order) and which sections say where they do work. So the 8.10 per-context scoping above no longer applies to what is *listed*, only to ordering and availability; what the recognizer *accepts* in each context is unchanged. `tests/test_command_reference.py` fails if a phrase in any `*_PHRASES` table is missing from the list, if a listed phrase does not resolve in the contexts its card names, or if the component or any page carries command text of its own.

**Implemented (Milestone 8.12):** the router grows from per-screen commands to the whole-app set, and gains a way to nest scopes.
- *Globals.* `GLOBAL_PHRASES` gains `OPEN_PDF` ("open a pdf"), `OPEN_SETTINGS` (moved from `HOME_PHRASES`) and `GO_RECENT` ("go to recent"/"show recent files", replacing Home's `SHOW_RECENT`), beside the existing `HELP`. Each screen's `VOICE_ACTIONS` decides what they mean there: Home opens its dialog; Settings leaves a one-shot `localStorage` note (`lector-open-dialog`) and navigates to Home, which opens the dialog on arrival (the Open dialog only exists on Home); Reading does the same but only after `promptSaveIfDirty`, so leaving by voice never skips the unsaved-highlights check.
- *`OPEN_NUMBER`.* "open number N" (Home) is parsed like `GOTO_PAGE` — a lead phrase fuzzy-matched against `OPEN_NUMBER_PREFIXES`, then a spoken number — and opens `displayedEntries[N-1]`, the same ordering the picker's badges use, so the two cannot disagree. Unlike the picker's bare numbers it needs the lead, since nothing on screen says numbers are live.
- *Modal scopes.* `Api.push_voice_context`/`pop_voice_context` keep a stack, so a modal gives back whichever grammar it covered rather than a hardcoded one. `set_voice_context` clears the stack (a page declaring itself is a fresh baseline, and any modal still pushed belonged to a page already left); popping an empty stack is a no-op, so a close handler that runs twice cannot pop past the screen. Two contexts use it: `REFERENCE` (the "What can I say?" panel — only "got it"/"go back"/"cancel", so "next page" no longer turns pages behind it; there is deliberately no bare "close", one misheard word from "close app") and `OVERWRITE_CONFIRM` (Settings' "confirm overwrite"/"cancel"; the phrase is two words on purpose, since a bare "yes" is too easy to produce by accident). Both are **really modal**: `MODAL_ALLOWED_GLOBALS` lets only `HELP`/`START_DICTATION` through in `REFERENCE` and nothing in `OVERWRITE_CONFIRM`, in `resolve` *and* in the recognizer's vocabulary, so "quit" or "open settings" cannot fire behind a dialog (before, they were inert only because each page's listener happened to swallow them). On the frontend, `voice.js`'s `createVoiceScope(context)` wraps push/pop: every bridge call goes through one shared queue, because pywebview runs each on its own thread and a close that landed during the open's push used to pop first (or not at all), leaving the screen's commands dead; it also makes double-open/close idempotent and never pops a failed push. `Api` guards the stack with a lock. Dictation now pushes on top of `REFERENCE` and pops back to it, which replaces the hardcoded `reading` return described under 8.8 — the panel is now opened from Home and Settings too.
- *One registry.* `reference.py` is the single source for both the panel and the empty state's "TRY SAYING" chips (`try_saying(context)`, carried in the `get_command_reference` payload). Both are built from `router`'s tables, a test checks that every phrase either shows resolves through `router.resolve`, and another that the page's `VOICE_ACTIONS` handles its intent — so neither can advertise a command that does nothing.
- *Voice can't switch voice off.* No intent exists for it, and tests assert the phrases resolve to nothing in any context. Settings' toggles remain mouse/keyboard only.
- *Status honesty.* The sidebar voice box (`frontend/js/voice-box.js`, shared by Home and Settings) starts as "CHECKING VOICE", says "VOICE READY" only once the engine has answered and the page's `set_voice_context` succeeded, and says plainly when it didn't. The old hardcoded "VOICE READY" claimed readiness before either was true.
- *Push-to-talk and focus.* `voice.js`'s `shouldIgnoreKey` used to give way to every focused button, so after any click in the sidebar holding Space did nothing. It now gives way only to a control focused *by keyboard* (`:focus-visible`), where Space is how they mean to press it; a button merely clicked no longer swallows it.
- *Drag-and-drop.* Split across the bridge because the page only ever sees a dropped file's name, never its path. `Api.bind_file_drop(window)` registers a pywebview `drop` handler (with `prevent_default`, or the WebView navigates to the file and replaces the app with a bare viewer) on every `window.events.loaded`, since pywebview forgets DOM bindings on navigation. `features/home/file_drop.py` picks the PDF (`pywebviewFullPath`, `.pdf`, an existing file; first PDF wins; refusals carry a message) and `Api` forwards the outcome as a `lector:filedrop` event. `frontend/js/filedrop.js` cancels `dragover` for file drags (what makes the page a valid target), shows the "Drop a PDF to open it" overlay, and hands the path to the page's `onFileDrop` handler. It only reacts to drags carrying `Files`, so dragging selected text is ignored. Opening is each page's decision, which is why Reading prompts about unsaved highlights first and no page opens anything while a dialog is up.
- *Shared help panel.* `command-reference.js` now builds the panel's markup itself and `reference.css` is in `frontend/shared/`, so Home, Settings and Reading each load one script instead of carrying a copy.

**Implemented (Milestone 8.11):** `router.GLOBAL_PHRASES` gains `CLOSE_APP` ("close app"/"quit"), the one global command held back at 8.4 pending this milestone's dependency on the close gatekeeper above. `api.py`'s new `close_app()` method is deliberately thin — it looks up `webview.windows[0]` and calls `window.destroy()`, the exact same call `handle_window_closing()` itself makes to reissue a confirmed close. Because `window.destroy()` (via WinForms' `Window.Close()`) fires `FormClosing` the same way the OS close button or Alt+F4 does, it re-enters `window.events.closing` and therefore `handle_window_closing()` on its own, so the dirty-document check and save-or-discard prompt from 8.1 apply unchanged — no separate close logic was written for the voice path. `home.js`/`reading.js`/`settings.js` each gain a `closeApp()` calling `callApi("close_app")`, wired into their `VOICE_ACTIONS` tables the same way `GO_HOME` already is; unlike `GO_HOME`, `home.js` wires it too, since quitting is never a no-op the way "go home" is on the screen that already is Home. Like the rest of the global set, "close app"/"quit" is not yet listed in the "What can I say?" panel (8.10's scoping did not add global commands to it, since none were listed there before either).

## Saving: all or nothing (hardening H2)

Both kinds of save go through `features/reading/safe_write.py`, which holds no PyMuPDF (the document passes in how to write and check the file). `write_atomically(dest, write, verify, swap)` writes to a `.lector-save-*.tmp` file in the destination's own folder, fsyncs it, has `PdfDocument._verify_saved` reopen it (opens, needs no password, same page count, same per-page highlight counts as the open document), copies the destination's permission bits onto it, and only then moves it over the destination with `os.replace` — retried briefly on a Windows sharing violation, since an antivirus scan or the indexer can hold a fresh file for a moment. The temporary file is always removed. So the file at the destination is only ever the old one, intact, or the new one, complete; a failure anywhere leaves it byte-for-byte as it was and the highlights open and unsaved (`is_dirty` stays true).

- **Overwrite** no longer uses `saveIncr()`. It writes the whole document (which also makes a PDF MuPDF repaired on open savable; `saveIncr()` refuses those). Before touching anything, `safe_write.check_writable` opens the original for writing, so a read-only or locked file is reported while nothing has changed; on macOS this is also what stops `os.replace` from putting a new file where a read-only one was. Windows will not replace a file PyMuPDF has open, so `PdfDocument._swap_into_place` closes the document, moves the new file in, and reopens it. Page, zoom, OCR state and the undo/redo stacks live on `PdfDocument`, not on the `pymupdf.Document`, so they carry over; the stacks name highlights by xref, and a save without `garbage=` keeps xrefs (verified), with `_forget_history_if_stale` clearing them if that ever stops being true. If the move fails after the close, the document is reopened from the written file's bytes, so the reader keeps every highlight (in the unlikely case those cannot be read back, the original is reopened as it is on disk and the message says the unsaved highlights are gone, `HIGHLIGHTS_LOST`; if not even the original opens, `UNSAVED_NOT_REOPENED`, handled as below). Once the move has succeeded the save has happened, and nothing after it is reported as a failed save: `is_dirty` is cleared at once, flushing the folder is best-effort, and reopening the new file is retried briefly and then done from its bytes. If even that fails (`SAVED_NOT_REOPENED`), the document is let go of rather than left closed, and `perform_save` returns `closed: true` (`SaveError.closes_document`) with a message saying the highlights were saved; Reading then goes Home. `encryption=PDF_ENCRYPT_KEEP`, as `saveIncr()` had. A **signed** PDF (`get_sigflags() > 0`) is refused: rewriting it would break the signature; a copy is still allowed.
- **Save a copy** refuses the open PDF itself under any spelling (`safe_write.same_file`; on a Mac MuPDF could otherwise unlink the open original before writing). Before it is called, the Save-As screen asks `api.describe_save_target(path)`; when the path is taken by another file, `frontend/pages/replace-dialog.js` asks "Replace “name”?" (its own modal voice scope, `router.REPLACE_CONFIRM`: "confirm replace"/"replace it"/"cancel", no globals), and Cancel goes back to the Save-As screen on the same folder and name. `api._suggested_copy_path()` skips taken names (`name (highlighted).pdf`, then `name (highlighted) (2).pdf`, …).
- **Errors.** `safe_write.SaveError` carries a reason (read-only, no permission, locked, disk full, folder missing, file missing, drive gone, check failed, signed, the open file) and a sentence for the reader. `Api.perform_save` returns that sentence as `error`; anything else is logged and returned as the generic save message, never `str(exc)`. `reading.js` shows it with `alert`, as before.
- **Not covered:** a hard kill between writing the temporary file and the move leaves that `.lector-save-*.tmp` beside the PDF (the original is intact; nothing cleans it up). An overwrite creates a new file at the same path, so creation date, extended attributes and hard links are not kept.

## File tools (Milestone F1)

Compress, Make searchable, Export as images and Convert to PDF (`docs/PRD.md` § "Post-v1: file tools"). `features/file_tools/`:

- **Where the work runs.** In the OCR worker process, never on a bridge thread or a plain thread: PyMuPDF holds the GIL for a whole call. `OcrRunner.call(fn, args, timeout, abort)` (`reading/ocr.py`) queues any module-level function on the same single-process pool and the same `lector-ocr` queue as highlight OCR, and returns a `Future`. OCR and file work therefore never run at once, and the OCR path itself is unchanged. A call fails with its own exception, `WorkerLost` (timed out, or the pool's worker process id changed under it: a crash is noticed at once, not at the timeout) or `CallAborted`. Both end with `_discard_pool()` (the existing timeout path), so the next call starts a fresh worker.
- **Jobs are steps.** A tool's job (`tools.py`) is a run of short worker calls: open the PDF, one call per page or input file, write, check, close. What a job has open lives in a dict in the worker (`engine._OPEN`) between calls. If the worker is replaced, that state is gone and the next call fails cleanly (`JobMissing`). Highlight OCR slots in between steps, so a reader highlighting a scanned page waits at most one step.
- **Progress and cancel.** `jobs.FileJobRunner` runs one job at a time on its own `lector-file-job` thread; a second start is refused (`busy`, shown as "Another file job is running"). The job reports `{id, tool, state, phase, current, total, unit}` through `JobContext.progress`, and `Api._on_file_job_event` pushes it to the page as `lector:filejob` (`_dispatch_page_event`). The end event carries `state` done / failed / cancelled and the `result`, or a sentence from `messages.py` (Save's wording rules, always ending "The original is unchanged."; never library text). Cancel sets an event checked before every step, so a page-by-page job stops at the next page; a step marked `long` (Compress's image pass, writing a large file) is stopped at once by ending the worker. `JobCancelled` is a `BaseException`, so the `except Exception` in `safe_write` can't mistake it for a write failure. `Api.get_file_job()` gives a page that has just loaded the running job.
- **Compress progress is by phase.** MuPDF's `Document.rewrite_images` (present in the pinned 1.28.2) rewrites every image in one C call with no callback, so there is no page to report or stop at. Compress shows five phases ("Copying the document", "Compressing images" with an indeterminate bar, "Subsetting fonts", "Writing the file", "Checking the file"), and a cancel during the image pass ends the worker.
- **All or nothing.** Files are written only through `jobs.write_file`, which is `safe_write.write_atomically`: a temporary file beside the destination, fsynced, reopened and checked in the worker (`engine.verify_output`: page count; annotation types per page where the tool keeps them; needs a password exactly when the source did), then moved into place in one step. Compress's "less than 5% smaller" is a check that discards the temporary file, so nothing is written. Export writes into a `.lector-export-*.tmp` folder beside the destination, checks the file names, and renames it into place in one step, taking the next free name if one appeared meanwhile; it never writes into an existing folder. A cancelled or failed job leaves nothing behind.
- **The reader's document as it is now.** `PdfDocument.snapshot()` is `tobytes(deflate=True, encryption=PDF_ENCRYPT_KEEP)` under the save lock, with no garbage collection (it would renumber the xrefs the undo stack names). The open document's unsaved state, undo history and file are untouched. The held password goes to the worker in memory only. From Home the worker opens the file itself; a protected one asks for its password first (`file_tool_info` answers `reason: "password"`), which is held in `Api._tool_source` for that file's job only.
- **The bridge checks everything.** `start_file_job` validates the tool, every choice (`choices.py`), every page number, every input's type and existence, and the destination (next item). `show_in_folder` accepts what a job wrote this session as well as Recent; a folder is opened, a file selected.
- **Where a tool saves (F1.10).** `file_tools/destinations.py`. The page never sends a path for the output: it sends a folder and a bare name, and `destinations.check` builds the path, adding the tool's fixed extension (".pdf", none for Export's folder). It refuses a name that is empty, only dots, or holds a character Windows doesn't allow (`\ / : * ? " < > |`, control characters), so a name can't reach another folder; a folder that isn't absolute, isn't there or can't be written to; and a path that is one of the sources, however spelled (`safe_write.same_file`). "Writable" is asked of the folder itself, by making and removing an empty `.lector-check-*.tmp` there, since on Windows `os.access` only reads the read-only flag. The page asks the same questions first, so the answer can go under the right row: `check_output_folder` as soon as a folder is chosen, `check_tool_destination` as the primary button is pressed (`exists` then brings the existing "Replace “name”?" question in whichever folder was chosen; a folder export never asks, it takes the next free name). The name the dialog suggests is the first free one in the chosen folder (`suggest_tool_name`, `naming.free_stem`), and follows the folder until the reader types. Every dialog opens on the original's folder; the job's result carries `where` ("beside the original", "beside the first file" for Convert, "on the Desktop", "in Documents", "in <folder>"), which the result line and the finished toast use.
- **The "Save in" menu's places.** ON THIS PC is Desktop, Documents and Downloads from the OS's known-folder lookup, the one the Open dialog's Quick access already used: `dialogs/browser.known_folder` asks the Windows shell (`SHGetKnownFolderPath` with `FOLDERID_Desktop`, `FOLDERID_Documents`, `FOLDERID_Downloads`, so a OneDrive-redirected Documents is the real one) and is `~/<name>` elsewhere; never a hard-coded path, and a folder that isn't there is left out. RECENT is `settings.json`'s `recent_output_folders`: at most three absolute paths, most recent first, one entry per folder by normalised path (case, separators); a folder chosen with "Choose another folder…" or picked again from RECENT goes to the top once it passes the writable check, the ON THIS PC folders take no slot, and folders that are gone are dropped (and the file saved) each time the menu opens (`get_save_places`). RECENT is never a default.
- **The folder picker.** "Choose another folder…" opens the in-app file browser (`ensureSaveAsDialog`'s dialog, `createFileBrowser` in `js/file-browser.js`) with `open({ pickFolder: true })`: it lists folders only (`browse_directory(path, "folder")`, `dialogs/browser.FOLDER_FILTER`, an empty extension set), hides the file name row, and its confirm button reads "Use this folder"; confirming (or "save here") resolves to the folder being shown. Never a native dialog, so it stays voice-drivable: the same `save_dialog` context, numbered rows and place names. The "Save in" menu itself has no voice of its own (the numbered-overlay picker covers Home's Recent cards and the outline, not a dialog's listbox): it is mouse and keyboard, and "Choose another folder…" is the voice route to another folder.
- **Engine choices.** Compress: `subset_fonts()`, then `save(garbage=4, deflate=True, clean=True, encryption=PDF_ENCRYPT_KEEP)`; Balanced and Strong rewrite colour and grey images above 165 / 106 ppi down to 150 / 96 ppi with bicubic resampling (MuPDF's "average" only halves) as JPEG at quality 80 / 65, only when smaller (`FZ_RECOMPRESS_WHEN_SMALLER`), never enlarging; 1-bit images are left alone (`FZ_RECOMPRESS_NEVER`); soft masks and annotations are untouched. Export: `get_pixmap(dpi, annots=True, alpha=False)`, the page turned as shown. Convert: each input opened as its extension's type (`formats.py`), EPUB and FB2 laid out on A4, `convert_to_pdf()` then `insert_pdf()` in list order; on A4/Letter each image page is placed with `show_pdf_page`, fitted, centred, never above its size at 96 ppi; a GIF is its first frame. WebP is not offered: this MuPDF can't decode it.
- **Make searchable: the text layer.** Invisible text (render mode 3) written from the OCR word boxes, one `insert_text` per word, sized from the box's height (Helvetica's measured box: 1.374 × the font size, the baseline 0.299 above its bottom) and stretched along its own direction to fill the box's width. OCR reads a page as it is shown, so on a page turned by /Rotate a word runs across the screen: it is placed from its box as shown, written turned by the page's rotation (checked at 0, 90, 180 and 270°, where a search finds it within 3pt of where the picture shows it and the line reads in order). The page's own content and image are untouched: text is only added. Rejected: merging the page `pdfocr_tobytes` produces under the original, which brings a second, re-rendered copy of the image and has to be lined up on rotated pages. The words come from the open document's in-memory OCR, else the OCR cache under the same `page_key` highlighting uses, else `ocr.recognize` in the job (deskew, despeckle, up to three reads); new reads go into the cache, except a password-protected PDF's. A page whose text isn't readable (`ocr.is_readable`) gets none and is listed in the result; if no page gets any, nothing is written.
- **PyMuPDF guard rail.** `file_tools/engine.py` is the one new module allowed to import PyMuPDF (`tests/test_guard_rails.py`): it runs only in the worker, and keeping the file tools' MuPDF calls out of `document.py` keeps that file about the open document. `tools.py`, `jobs.py` and the rest import no PyMuPDF.
- **Closing while a job runs.** `handle_window_closing` asks first, through `confirmStopFileJob()` (`frontend/js/file-jobs.js`, on every page): Keep running cancels the close; Stop and close cancels the job, waits up to 10s for it to clean up, and closes again, which brings the unsaved-highlights question if there is one.
- **Drops.** The page never sees a dropped file's path, so `home/file_drop.py` adds `convertible` (dropped images and e-books on disk) to `lector:filedrop`. Home's Convert dialog takes them while it is open; anywhere else the refusal gains "To make a PDF from it, use Tools › Convert to PDF." The Open dialog lists them when asked for the named filter `convert` (`dialogs/browser.py`), never extensions from the page.
- **Frontend.** `js/file-jobs.js` follows `lector:filejob` on every page and shows the finished toast when no dialog is watching the job. `pages/tool-dialogs.js` is the Compress / Make searchable / Export dialog (reader and Home), `pages/convert-dialog.js` Convert to PDF, `pages/tools-page.js` Home's Tools page and the "choose a PDF" step, `pages/file-menu.js` the reader's More menu and footer pill, `js/popup-menu.js` the menu behaviour shared with the Recent row menu, `js/save-destination.js` the Name + "Save in" block every tool dialog shares (made once per dialog open and moved back in on every re-render, so the field keeps its text and focus). The Save-As dialog (`ensureSaveAsDialog` in `file-browser.js`) and the "Replace?" question (`replace-dialog.js`) now build their own markup, so Home has them too. Remembered choices (last Compress level, Export format and resolution) are `settings.json`'s `file_tools`, checked on read.
- **Voice.** Reader phrases in `command_grammar.PHRASES` (`COMPRESS_FILE`, `MAKE_SEARCHABLE`, `EXPORT_IMAGES`), Home's `OPEN_TOOLS`, and one modal context for every tool dialog, the picker and the close question, `router.FILE_TOOL`: "confirm" (`TOOL_CONFIRM`, the primary button), "cancel", a bare number (`DIALOG_PICK`); no globals pass.

## Page changes (Milestone F2)

*Design gate (F2.1): approved, with the four refinements below (restoring the shared refs' xrefs, redo by swap, refs of deleted pages set aside, permissions checked by the reader). The spike stays as regression tests in `tests/test_page_changes.py`.*

Organise pages (rotate, delete, reorder, extract, insert) changes the open document's pages. The reader's undo stack already holds highlight edits (`_Edit`) that name their page **by index** and their annotation **by xref**, through a shared, mutable `_HighlightRef` that an undone removal repoints when it re-adds the highlight under a new xref. A page change has to live on that same stack without invalidating either.

- **Organise edits a draft, not the document.** It holds a page plan: an ordered tuple of entries, each a source page (the open document's page index, or a page of an inserted source) and a rotation, plus a "new" mark for inserted pages. Rotate, delete, move and insert make a new plan; nothing touches the `pymupdf.Document`. Organise has its own fine-grained Undo/Redo over plan states. The plan lives in Python (`features/reading/page_plan.py`, pure, no PyMuPDF), so Done, Extract and the tests share one authority; the page keeps only the selection, focus and drag state. Thumbnails are drawn from the plan (source page, rotation applied).
- **Done applies the plan as one edit.** `PdfDocument.apply_page_plan`: take `snapshot()` (`tobytes`, no garbage collection, encryption kept); append each inserted source with `insert_pdf`; `select(order)`; `set_rotation` per page. It is pushed on the undo stack as one entry, "Page changes", which (like any new edit) clears redo. The PyMuPDF calls that turn a plan into pages live once, in `file_tools/engine.py`, called on the live document from `document.py` (as `describe_document` already is) and on a worker copy by Extract.
- **`select()`, not `delete_pages()`.** MuPDF's rearrange keeps every surviving object's xref (so a moved page's highlights are still found by the xrefs their edits name), drops outline items and links that point at a deleted page, and retargets the rest to their page's new position. `delete_pages()` would leave a bookmark pointing at page −1. So Lector never reads or rewrites links itself, and the guard rail against reading link actions (`tests/test_untrusted_pdf_content.py`) stands unchanged.
- **Undo and redo swap.** The entry always holds exactly one *other* state of the document: the one before the change while it is applied, the one after while it is undone. Undo or redo captures the current state into the entry and puts the held one back. Memory is one snapshot per entry, and a redo returns exactly the document (and xrefs) that edits above the entry name. A state is three things:
  - the bytes, reopened with `_open_unlocked(stream=…)`, so a password-protected PDF needs its password and keeps its protection;
  - the live `_refs` map;
  - the xref of every `_HighlightRef` the stacks name. This is required, not tidy-up: with the stack E1 (add) | page change | E2 (remove), undoing E2 re-adds the highlight under a new xref and repoints the shared ref, and a restore of bytes alone leaves E1 looking for that new xref in a document that doesn't have it (the spike shows the crash).
- **Order is the stack's.** An edit below the page change names pre-change page indices, so it is only reachable after the page change is undone; an edit above names post-change indices. The single stack guarantees both. Code that peeks at the top of the stack (the opacity/width gesture merge in `set_highlight_appearance`) must treat a page-change entry as "not my gesture".
- **A highlight on a deleted page.** Applying the plan keeps in `_refs` only the refs whose xrefs are still highlights on some page; the others stay in the entry's held state. Otherwise the staleness check after an overwrite save (`_forget_history_if_stale`) would see a ref with no live highlight and clear the whole history.
- **Limits.** At most 3 page-change entries across both stacks, and at most 300 MB of held bytes. Pushing a 4th (or passing 300 MB) drops the oldest page-change entry **and everything below it** on the undo stack (an edit below a dropped change could never be reached again). The next `_state()` carries a one-shot flag and the reader shows "Older changes can no longer be undone." once. Measured: a 220-page text PDF snapshots to 82 KB in 38 ms; a snapshot is about the file's size, since images are copied compressed.
- **What else changes on apply, undo and redo.**
  - The in-memory OCR state (`_scanned`, `_ocr_keys`, `_ocr_status`, `_ocr_text`) is keyed by page index, so it is cleared and the OCR generation bumped (a result in flight is dropped). The disk OCR cache is keyed by page content and refills it without re-reading, except for a scanned page that was rotated: `ocr.page_key` includes the rotation, so that page is read again.
  - The current page follows its identity (if it was deleted, the nearest earlier page that survives).
  - Find results are cleared, and the page re-reads highlight counts, outline and page count.
- **Nothing reaches the disk until Save.** Save and Save a copy write it through the existing all-or-nothing path (`_verify_saved` already compares page count and highlights with the open document; a signed PDF still can't be overwritten). Once a page change has been applied in this session, both saves use `garbage=1` (`PdfDocument._pages_changed`): without it a deleted page's objects stay in the file, unreferenced but readable by anyone who looks. `garbage=1` drops unused objects **without renumbering** (verified: the live document's and the file's highlight xrefs are unchanged), so undo history survives the save; only `garbage=2` and above compact. Extract and Split write new files, so they collect unused objects too and never carry a deleted page's objects.
- **Which PDFs can be changed.** A document must be open and loaded, and its permissions must allow changes: MuPDF does not enforce them (`select()` succeeds on a PDF whose owner forbade modifying and assembling; verified), so the reader does (`PdfDocument.page_change_block`). Organise is enabled when either the modify or the assemble bit allows it, and disabled only when both forbid it, with the tooltip "This PDF's owner doesn't allow changing its pages." A PDF unlocked with its owner password has every permission. Extract and Split apply the same check to their source.
- **As built (F2.2).** `reading/page_plan.py` (the draft and `PlanHistory`), `reading/page_changes.py` (the `PageChange` entry, its `DocState`, which page the reader lands on, the caps; no PyMuPDF), `PdfDocument.apply_page_plan` / `_step_page_change` / `page_change_block` / `add_page_source` (Insert's files, opened from bytes, held until Done), and `file_tools.engine.apply_page_plan`. The bridge: `organise_begin`, `organise_action(kind, args)` (`rotate`, `delete`, `move`, `shift`; it answers with the new draft and the pages to select), `organise_undo` / `organise_redo`, `organise_thumbnail(source, index, width)`, `organise_done` (applies; on a failure the document is as it was and the draft stays open). `_state()` gains `undo_kind` / `redo_kind` ("highlight" or "page_changes") and `organise_blocked`; undo and redo answer `pages_changed` and `history_trimmed`. While a draft is open the reader's own Undo/Redo do nothing (the draft is of the document as it is; Organise's Undo is `organise_undo`). Every page change forgets the voice viewport, which names pages by index; the page sends a new one once it has laid out again.
- **Reads and page changes kept apart (F2.3).** pywebview runs each bridge call on its own thread, so page images, the strip's look-ahead, the Organise grid's and the outline panel's thumbnails and find can all be reading the document when Done, Undo page changes or Redo page changes runs. `reading/doc_gate.py`'s `DocGate` keeps them apart: every `PdfDocument` method that reads pages is `@_reads` (re-entrant per thread), and `apply_page_plan` / `_step_page_change` take `changing()`, which waits for every read already running and holds back reads asked for meanwhile; the changing thread may read. A page index asked for before a change and answered after it may no longer exist: `render_page` returns None for it, and `render_page_sized` renders and sizes a page in one read, so a change can't fall between the two. `tests/test_page_change_renders.py` holds a thumbnail mid-render while Done is pressed, holds an Undo mid-swap while a render is asked for, and runs renders on three threads through repeated Done/Undo/Redo.
- **One lock order, everything that touches the document gated (F2.3 review).** A code review of the gate found that saves took `_save_lock` and then, in their check, a gated read, while a page change took the gate and then `_save_lock`: a save and a Done at once deadlocked. Now every `_save_lock` holder enters the gate first (saves, `open`, `close`, page changes, history steps; `snapshot` as a read), so the order is always gate, then lock. Undo and redo are one `step_history` under the gate and the lock: the entry is popped, applied and pushed in one piece, and its kind (highlight or page changes) comes back with it, so two quick Ctrl+Z can't interleave, can't be misreported to the page, and an `open` arriving meanwhile can no longer be overwritten by a stale page change. `apply_page_plan` checks the plan against the document inside the same lock. Highlight writes, OCR status and start, and the file tools' reads of the open document are gated reads too, so none of them can land between a change's snapshot and its swap. Reads still run alongside each other on the one MuPDF document, as before; the gate only keeps changes apart from reads. On the page: steps queue one behind another and follow what the backend says each took back; the busy card's note is taken out of sessionStorage as the reloaded page starts and the card comes down whatever the reader's start-up does; a file dropped during a change is ignored; a failed Done keeps the draft and lets its thumbnails load again. Tests: `ReviewRaceTests` (a save and a Done at once; an open while an undo waits; two quick undos), and Organise's failed-Done behaviour.
- **Leaving Organise without applying (F2.3).** Cancel (or Esc, or the spoken "cancel") drops the draft through `Api.organise_cancel`: no snapshot, no busy card, nothing recorded, and the reader exactly as it was. With changes in the draft it first asks "Discard page changes?" (`pages/organise-discard.js`, the danger dialog pattern; Keep editing is focused and is what Esc means). Organise's voice context, `router.ORGANISE`, hears "done" and "cancel" now (the rest of its grammar comes with F2.10) plus every global; the discard question is a modal `file_tool` scope ("confirm" discards). Closing the window or going back to the Library still applies the draft first and then asks the usual question.
- **The reader after a page change (F2.3).** Every per-page cache in the reader (page images and the strip, characters and highlight targets, the outline and progress bar thumbnails, find results, OCR waits) is keyed by page index, so after a real change the reader page reloads, as it does to open a dropped PDF, and reads the document afresh. "Applying page changes…" (`pages/page-change-busy.js`) goes up within a frame of the click, before Python has been asked; it blocks the mouse, keys and voice, and stays up across the reload (`js/page-change-pending.js` in `<head>` keeps it from the reloaded page's first frame) until the document has been drawn again. A note in sessionStorage carries the toasts across ("Page changes are unsaved. Ctrl+S saves them with your highlights." after Done; "Older changes can no longer be undone." when the caps trimmed). Done with nothing changed closes Organise at once: no snapshot, no busy card. Leaving the reader with Organise open (the Library, another PDF, the window closing: `promptSaveIfDirty`, and `Api.handle_window_closing` counts a draft with changes as unsaved) applies the draft first without a reload, then asks the usual question; staying after all reloads onto the changed pages.
- **Insert (F2.5).** `Api.organise_add_source(path, password)` opens the chosen file and hands it to `PdfDocument.add_page_source`, which holds it (from bytes) under a source id until Organise ends: a PDF is read as it is and unlocked with the password, which is never stored; an image or e-book is made into a PDF first in the worker process (`file_tools.engine.convert_to_pdf_bytes`, Convert's "Same as image" path, so PyMuPDF stays in the worker and in `document.py`). `organise_action("insert", {source, gap})` puts every page of it in as one plan step (`page_plan.insert`; a source goes in once). A file chosen and then not used (another chosen with Choose…, or the dialog cancelled) is let go with `organise_forget_source`, unless a plan in the draft's Undo/Redo still has its pages (`PlanHistory.uses`); `drop_page_source` takes the gate, so no thumbnail is mid-draw from it. Done and Cancel let go of every source, as before. The file is picked in the reader's own Open dialog (`js/file-browser.js`'s `ensureOpenFileDialog`, kind `"insert"`: PDFs and Convert's types, `dialogs/browser.py`'s `INSERT_FILTER`). Tests: `tests/test_organise_insert_api.py`.
- **Measured end to end (F2.3, after the review fixes)**, from the click until the web view has painted the redrawn reader, in a real WebView2 window at 1280×800: a 1,000-page text PDF, Done 0.76 s, Undo page changes 0.73 s, Redo 0.68 s; a 110 MB scan (58 pages) 1.84 / 1.56 / 1.38 s; a 247 MB scan (130 pages) 2.52 / 2.79 / 3.26 s. The busy card was on screen at the next frame every time (1–24 ms after the click), and each change waited 0 ms at the gate (nothing was rendering). One earlier run was 2–3× slower throughout with the same 0 ms waits, so machine load rather than the gate.
- **Measured (F2.2, Python side, including the reader's redraw calls: the state, the current page's image at a 1.5 pixel ratio, every page's size and the outline).** A 1,000-page text PDF (0.6 MB): Done about 0.4–0.5 s, Undo and Redo about 0.26–0.28 s. A 110 MB scan (58 pages): Done 1.6–1.9 s, Undo 2.1 s, Redo 1.7 s; the third Done passes 300 MB and drops the oldest change. A 247 MB scan: 2.6–4.4 s, and the second Done already drops the first. The time is `tobytes` (the snapshot) and `select()`, both holding the GIL, plus rendering a dense page. So Done, Undo page changes and Redo page changes show "Applying page changes…" and block input while they run (built with the view, F2.3). On big scans the byte cap is what bites (the second Done on a 247 MB scan already drops the first); that is accepted as built. Rejected: undoing by running the plan in reverse instead of holding a snapshot. It can't bring back a deleted page without storing it, so it would only save bytes for reorders, rotations and inserts, at the cost of a second undo path.
- **Possible follow-up (not built).** If the cap proves a problem in real use, hold the snapshots in temporary files on disk instead of in memory (deleted on close, cleaned up at the next startup after a crash), with no other design change.
- **Spike results (`tests/test_page_changes.py`, PyMuPDF 1.28.2).**
  - A highlight on page 3, then a plan that deletes page 2 and moves page 3 to the front, turned 90°: the highlight is on index 0 under the same xref. Undoing the change restores four pages, the original order and rotation, and the same xref, after which the highlight's own undo removes it. Redo walks back up to the same state.
  - E1 | page change | E2 undoes and redoes in step only with the ref xrefs restored.
  - A deleted highlighted page keeps the history through an overwrite save.
  - A password-protected PDF round-trips with its xrefs and stays protected in the snapshot.
  - Plus the MuPDF behaviours above: bookmarks and links, `delete_pages`' −1, `garbage=1`, permissions not enforced.

## Errors and logging (hardening H3)

- **The log file.** `shared/app_log.setup` writes `lector.log` into `logs/` next to settings.json (`settings.settings_dir()`: `%APPDATA%\Lector\logs` on Windows, `~/Library/Application Support/Lector/logs` on macOS, `~/.config/lector/logs` elsewhere), rotated at 1 MB with 3 old files kept. Lector's own loggers (`lector.*`) are kept from INFO up, everything else (pywebview, libraries) from WARNING. `__main__` sets it up only after the single-instance lock is held, so one process owns the file: a second launch that hands over never opens it, and the spawned OCR worker never runs `main()`. Nothing is printed to stderr any more except by pywebview's own handler; the file is the place to look.
- **No content in the log.** Lector's log calls never pass document text, OCR output, highlight text, search queries or transcripts, and file *names* only where they help. The rest is enforced by `ContentFreeFormatter`: an exception is written as its type and its frames (file, line, function), never its message, since that is where a library quotes its input or a path; the same for an exception passed as a log argument, and for the frames of the OCR worker's `RemoteTraceback`. pywebview's records arrive with their tracebacks already flattened into the text (`util.py` logs `traceback.format_exc()` for every Api method that raises) and sometimes a value a page returned, so they are cut to frame lines and exception type, or to their first line. `tests/test_log_privacy.py` runs real paths with words planted in the PDF, the query, the transcript and the OCR text, and checks the log has none of them. The cost is that a log line says `RuntimeError (message withheld)` rather than MuPDF's own wording.
- **Uncaught exceptions.** `app_log.install_exception_hooks`: `threading.excepthook` logs the thread's name and traceback, then `Api.notify_background_error` calls `window.lectorBackgroundError()` (`frontend/js/background-error.js`), which shows one toast per page. `sys.excepthook` logs and, on Windows, shows a native message box (`MessageBoxW` through `ctypes`, no new dependency) before Python's own hook runs; on macOS there is no box, only the log. Bridge calls are not threads Lector starts: pywebview catches their exceptions, logs them (filtered as above) and rejects the page's promise, and the page shows its own fixed sentence, never `String(err)`.
- **Failures that used to be silent** are now logged: a voice result subscriber that raises (`VoiceEngine._emit`, without the payload), a speech or VAD model that won't load, a microphone that won't open, the first undecodable audio chunk of a session (once, since the loop runs eight times a second), a page that can't take an `evaluate_js` (DEBUG: that is what a page mid-navigation looks like), and an OCR worker that won't stop. The engine's `status()["error"]` is now one of `engine.MODEL_MISSING`, `MODEL_FAILED` or `MIC_FAILED`; the model path and the `scripts/fetch_vosk_model.py` hint go to the log. `request_microphone` and `browser.list_directory` return fixed codes (`microphone_unavailable`, `unreadable`) instead of `str(exc)`.
- **OCR worker crashes.** An exception inside `recognize` comes back pickled and is logged by the parent, as before. A native crash (Tesseract or MuPDF taking the process down) has no Python exception, so the pool is started with `_worker_init`, which turns on `faulthandler` into `logs/ocr-worker.log`: the stack it died in, frames only. The parent still sees it as the 120 s timeout, and its log line points at that file.
- **Not covered:** Python's own fatal errors before `setup` runs (a broken install, the single-instance claim itself) still only reach stderr. There is no in-app way to find the log folder; that would be a new feature.

## Settings file (hardening H4)

`features/settings/store.py` is the only code that reads or writes settings.json, and every setter is load → change → save of the whole file.

- **Written in one step.** `_save` writes `settings.json.tmp` beside it, flushes and fsyncs it, then moves it over settings.json with `safe_write.replace` (H2's `os.replace`, retried briefly on a Windows sharing violation; reused from `reading/`, which holds no PyMuPDF and imports only the standard library). The temporary file is removed in a `finally`. So the file on disk is only ever the old one or the new one, whole. A write that fails (disk full, another program holding the file past the retries) leaves the old one as it was and is logged, not raised: the change is simply not saved, and a setting is never why a PDF fails to open or a page fails to turn.
- **One writer at a time.** Bridge calls arrive on several threads (a page turn writes the reading position while, say, the outline panel is resized), and two setters interleaving used to save a copy read while the other was writing, emptying Recent and Favorites. A module `RLock` is held by every read and, through the `@_serialized` decorator, by each setter's whole load-change-save. `tests/test_settings_file_safety.py` checks with an AST walk that every function calling `_save` has it. One process only: the single-instance lock already guarantees that, and the OCR worker never writes settings.
- **A damaged file is kept.** One that is there but doesn't parse (cut short, not UTF-8, not a JSON object) is renamed to `settings.json.corrupt-<YYYYmmdd-HHMMSS>` (`-2`, `-3`, … within the same second; the two newest such copies are kept), a warning naming the copy goes to the log, and the defaults load; the next change starts a fresh file. A UTF-8 byte-order mark (left by some editors) is accepted rather than counted as damage.
- **An unreadable file is not written over.** One that is there but can't be read (another program holding it is retried briefly; access denied is not) makes getters return defaults and holds writes until a read succeeds again: a change in the meantime is not saved, never raised. The same hold applies when a damaged file can't be renamed aside. The hold belongs to the outermost setter that found the problem (`_write_depth`), so neither a getter on its own nor a nested setter can leave or lift it. A problem that persists (unreadable, stuck, unwritable) is logged once when it starts and once when it clears, not on every read or page turn.
- **`schema_version`.** Every save stamps `SCHEMA_VERSION` (1), or keeps a higher number a newer Lector wrote. `_load` passes the file through `_migrate`, a no-op today (a file without the key is version 0, from before H4, and has the same keys); a future rename of a key goes there. Keys this version doesn't know are carried through every write untouched.
- **Not covered:** a hard kill can leave `settings.json.tmp` behind (settings.json itself is intact; the next save overwrites the temporary file). The folder is not fsynced after the rename, so on a power cut the very last change can be lost, never the file. Nothing in the UI says settings were reset or a change wasn't saved; the `.corrupt-*` copy and the log are the record, and while writes are held a setter's return value (e.g. `add_favorite`'s True) can describe a change that was not kept. Access denied is not retried, so a file another program is replacing at that instant reads as unreadable for that one operation. A file that stays held costs each read the 0.4 s of retries. A symlinked settings.json is replaced by a plain file, and the new file gets default permissions. The fixed `settings.json.tmp` name relies on the single-instance lock: two Lector processes writing at once would collide on it.

## Opening a PDF (hardening H5)

`PdfDocument.open(path, password=None)` is the only way a PDF becomes the open document, and `Api.open_pdf` the only bridge call to it.

- **Checked before anything is let go.** `_open_checked` opens and checks the new file completely first. Only then is the open document closed and the per-document state (page, zoom, undo/redo, OCR) reset. So a file that can't be opened leaves the PDF on screen, its unsaved highlights and its history exactly as they were. Before H5 the open document was closed first, and a failed open left the reader holding a closed one.
- **Why it failed, in words.** `features/reading/open_errors.py` holds the reasons and their sentences, like `safe_write` does for saving, and `PdfDocument.open` raises `OpenError(reason)`. The checks run in an order that gives the real reason:
  - Python first: not a file → `missing`, zero bytes → `empty`, can't be read (held by another program, no permission) → `unreadable`.
  - Then MuPDF, with `filetype="pdf"`: its `FileNotFoundError` (a `RuntimeError`, not an `OSError`) → `missing`, `FileDataError`/`ValueError` → `not_a_pdf`, anything else → `unknown`, logged without content (H3).
  - Then on the opened file: not a PDF after all → `not_a_pdf`; a password needed and missing or wrong → `password` / `wrong_password`; no pages → `no_pages`; a first page that won't load → `not_a_pdf`.
  - A truncated file MuPDF can repair still opens, as before.
- **What the page gets.** `Api.open_pdf` returns the reader's state as before, or `{"error": sentence, "reason": code}`, with nothing else changed: no Recent entry, and the `Api`'s title, path and voice viewport untouched. `frontend/pages/open-pdf.js` (`openPdf`) is the one caller on every screen. It shows the sentence as a toast, hands `missing` to the caller (Home offers "Remove from Recent"), and on `password` asks with `password-dialog.js` and calls again with the password until it opens or the reader cancels.
- **Password-protected PDFs.**
  - **Which ones ask.** Only a PDF that can't be read without a password (`needs_pass`); either of its passwords unlocks it. One with only an owner password (printing or copying restricted) opens without asking, as before.
  - **Held while open, never stored.** The password is kept on the `PdfDocument` (`_password`) only while that PDF is open, and dropped by `close()` and the next `open()`. It is never logged, written to settings.json or Recent, or returned to the page, and the page keeps it only in the field (emptied on close).
  - **Saving keeps the protection.** Both saves keep the password. Overwrite already wrote with `PDF_ENCRYPT_KEEP`. "Save a copy" now does too for a protected PDF, where MuPDF's default would write the copy unprotected. The check after a save (`_verify_saved`) and every reopen around it (`_reopen_saved`, `_reopen_from_memory`) unlock with the held password. The check requires the saved file to need a password exactly when the open one did.
  - **No OCR text on disk.** `finish_ocr` doesn't write a protected PDF's OCR text to the cache: the cache is plain text outside the PDF, readable without the password. Its scanned pages are read again each session.
  - **A PyMuPDF trap.** On PyMuPDF 1.28, reading `needs_pass` after `authenticate()` locks the document again, and every page then reads as empty, with no error. `_unlock` reads it exactly once, before unlocking. `tests/test_password_unlock.py` would catch a regression.
- **Voice.** The password dialog is its own modal scope, `router.PASSWORD_PROMPT`, hearing only "cancel". A password is typed, never dictated, since a spoken one would pass through the recognizer.
- **Untrusted content.** Nothing in `src/lector` reads a PDF's links, launch actions, JavaScript, embedded files or form fields; pages reach the web view as pictures. `tests/test_untrusted_pdf_content.py` opens a PDF carrying all of them, with every way of starting a program watched, and scans the source so a new launcher fails the build. The only allowed one is "Show in folder" (`recent.reveal_in_file_manager`).
- **Very large PDFs.** Nothing at open time walks every page except `page_sizes()` (strip view's placeholders). But `highlight_counts()` walks every page on each `_state()`, which is every page turn, zoom and highlight. Measured on generated PDFs: about 26–37 ms at 500 pages and 100–135 ms at 2,000; `page_sizes()` about 34 ms at 500. Left as is (H5's bar was "fix only if slow at 500 pages"); a per-page count kept up to date by highlight edits would remove it.
- **Not covered:**
  - The password is in the process's memory while the PDF is open (and, as a Python string, until it is collected); a memory dump would show it.
  - There is no limit on tries: the file is the reader's own, on their own disk.
  - A protected PDF's Recent card has no thumbnail.
  - The 2,000-page cost above.
  - Nothing was run on macOS.

## Naming convention

Python side: ecosystem standard — `snake_case` for files, modules, functions, and variables; `PascalCase` for classes. Frontend side: `kebab-case` for HTML/CSS file names and CSS classes (e.g. `save-dialog.css`, `.recent-card`), `camelCase` for JS variables and functions — the respective ecosystem standards for each, not a project-specific choice.
