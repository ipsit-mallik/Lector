# Product Requirements Document

## Problem

Adobe Reader's ~10GB install footprint is unjustified for the actual use case: read-only PDF viewing, nothing else. (Since v1, a small set of file tools has been added at the developer's request — see "Post-v1: file tools" — kept to what PyMuPDF does on its own, so the footprint goal still holds.) Separately, hands are frequently occupied while reading (eating, exercising, chores), making mouse-driven scrolling, page navigation, and highlighting impractical.

## Who it's for

- **v1:** the developer, personal use.
- **Future (conditional):** public open-source release if there's demand, and a portfolio/social-media piece regardless of adoption.

## Must-have v1 features

- Voice-driven page navigation: next/previous page, jump to page N, scroll up/down.
- Speech-to-match highlighting: user speaks a few words, app fuzzy-matches them against the text currently visible in the viewport and highlights the matched span. Word-level matching is the baseline; sentence-level highlighting extends the match to the nearest sentence-ending punctuation (heuristic, not full sentence-segmentation NLP).
- Disambiguation rule when a phrase matches more than once: scope matching to the visible viewport only (never search the whole document); on a tie within the viewport, the first occurrence in reading order (top-to-bottom, left-to-right) wins.
- Real PDF annotation persistence via PyMuPDF — highlights (and freehand strokes, as ink annotations) are written as actual PDF annotation objects, so they're visible in any standard PDF viewer, not just this app.
- Highlight colours: a fixed set of five — yellow (the default), green, blue, pink, orange — and no free colour picker. The colour chosen next to the highlight tool is the active colour for every new highlight, by mouse or voice, and is an app-wide setting remembered across sessions. Clicking (or tabbing to) an existing highlight lets the reader change its colour or remove it; both are undoable like adding one. Voice: "highlight <words> in <colour>" colours one highlight without changing the active colour, and "highlight color <colour>" changes the active colour. Colours are written into the PDF annotation itself (its colour entry and its appearance), so other viewers show the same colour. Added after v1 scoping, at the developer's request. Recolouring or removing an *existing* highlight by voice is not included: it would need a way to name one highlight among several by speech, which no command does yet.
- Freehand marking with the highlight tool: what is under the press decides, once per drag. On text (a text layer, or what OCR read on a scanned page) it is a text highlight, as before; anywhere else — a photo, a barcode, blank paper — it draws a marker stroke in the active colour — the same five colours as text highlights — as wide on the page as the chosen thickness (14pt unless changed in the highlight tool's settings) at every zoom, at the Highlight opacity (60% unless changed) through Multiply so what is under it stays visible and a stroke beside a text highlight of the same colour reads as that colour. Alt draws over text too. Shift draws a straight line, kept horizontal or vertical when within 5° of either; a stroke that is nearly straight (never more than 6% of its length off the line between its ends, and at least 24pt long) becomes that line on release, and the first Undo after that gives back the stroke as drawn. A stroke is a real PDF ink annotation with that opacity and blend mode, so other viewers draw it the same; it is counted, marked on the progress bar, recoloured, removed and undone like any highlight. A scanned page not read yet is read by the first press, as before; once read (or found to have no text) it is drawn on wherever there is no text. Drawing is pointer only, as a text drag is; every drawing is still a focusable control (Tab, Enter, recolour, remove), and voice highlighting stays text only. Added after v1 scoping, at the developer's request.
- The highlight tool, its styles and settings: the rail's highlight tool is a split button. The button turns the tool on and off in the current style, its icon showing which: Highlight, Underline or Strikethrough. A badge on its corner (or a right-click on it) opens a small card listing the three styles with their keys, H, U and S; choosing one turns the tool on. The keys do the same from anywhere in the reader — that style with the tool on, or the tool off when it is that style already — but never while typing in a field or behind a dialog. Under the tool a preview (a short line in the colour, at the style's opacity) opens a settings card: the five colours, Opacity and Thickness, with no style switcher, voice hints or keyboard hints of its own; one card is open at a time. Every choice applies at once and is remembered across sessions. Style is what a drag over text (a text layer or what OCR read) writes: a PDF Highlight, Underline or StrikeOut annotation, snapped to words and lines as before; an underline's or strikethrough's line is placed and sized from the text's own size and baseline. Over anything that is not text the tool always draws the freehand marker (Alt and Shift as before). Opacity is 10–100%, remembered per style (Highlight 60%, Underline and Strikethrough 100% by default) and written into each annotation; freehand strokes use the Highlight opacity, so a stroke matches a text highlight beside it; highlights and strokes multiply, lines are drawn plainly. Thickness is five presets for freehand strokes — 4, 8, 14 (the default), 24 and 36pt, in page units. The editor an existing highlight opens gains the same opacity slider, and the thickness presets for a stroke; changes apply live and are undoable (one slider drag is one undo step). Voice: "underline <words>" and "strike through <words>" (or "strike out"; "the sentence" and "in <colour>" forms too) match as "highlight <words>" does; "opacity <10, 20 … 100>" sets the current style's opacity (only those values); "thicker" and "thinner" move one thickness preset; "highlight mode", "underline mode" and "strike through mode" choose a style with the tool on; each is confirmed in the mic pill, and all are in "What can I say?" under Highlighting. Underlines and strikethroughs are highlights everywhere highlights are counted (the footer, the progress bar's markers, undo, the save prompt). A consequence of the 60% default: new text highlights are lighter than the solid colour they used to be; highlights already in a PDF are unchanged. There is no Highlights tab to show a style icon in. Added after v1 scoping, at the developer's request.
- Save-behavior preference: on the first explicit Save action, ask "Save a copy" vs. "Overwrite the original," with a "Don't ask again — remember this choice" checkbox (unchecked by default). The dialog is generalized to "Save changes?" — it is triggered only by an explicit Save action (voice command, click, or shortcut), never automatically as a side effect of highlighting or any other future edit. Saving is all or nothing: a failed or interrupted save never damages the original PDF or a file already at a copy's destination, and says in plain words what went wrong. "Save a copy" asks before replacing a file that already has the chosen name. A digitally signed PDF is never overwritten (that would break its signature); the reader is told to save a copy instead.
- Dual voice activation: push-to-talk (default key: Space) and a wake phrase ("Hey Lector"), independently toggleable; both remain available as fallback regardless of which is the default.
- Home screen "Recent" list: last 20 files, most-recent-first. With nothing in it, the empty state is the app's onboarding: a card with the Open PDF button, "or drop a file anywhere in this window", and a "TRY SAYING" row of example phrases (read from the voice command registry, never typed by hand).
- Drag-and-drop: dropping a PDF anywhere on the window opens it — from Home and Settings straight away, and from the reading view after the usual unsaved-highlights prompt. Anything that isn't a PDF is refused with a message. Added after v1 scoping, at the developer's request; the Open PDF button remains the equivalent for anyone not dragging.
- Opening a PDF that can't be opened: a file that is missing, empty, damaged, not a PDF or held by another program is refused with one plain sentence saying which ("The PDF couldn't be found. It may have been moved or deleted."), and the reader stays where they were, with the PDF that was open still open and nothing added to Recent. A Recent entry whose file has gone offers "Remove from Recent" from the same message (the usual confirmation; the file on disk is never touched). Hardening H5.
- Password-protected PDFs: a PDF that needs a password to open asks for it in a dialog ("Enter the password") and opens once it is right; a wrong one says so under the field. Either of the PDF's passwords works. The password is typed, never spoken, and never remembered: it is asked for each time the PDF is opened, held only while it is open, and never written to the log, settings or Recent. Saving keeps the protection (an overwrite and a copy both need the same password), and the text OCR reads from its scanned pages is not cached on disk. Added during hardening H5, at the developer's request.
- Resume reading: reopening a file from Recent returns the reader to the page, layout, and zoom level they left it on. Governed by a Settings preference ("Continue where I left off" — the default — vs. "Always start at the beginning"), so a reader who prefers every document to open at page 1 can have that. A document with no saved position — never opened before — always opens at the defaults (page 1, the default view from Settings > Reading — book unless changed — and 100% zoom), never with the previous document's view; "Always start at the beginning" uses the same defaults. Position is stored per document alongside its recent-files entry, so it is pruned automatically when the file falls off the 20-item list.
- Favorites: a star on each file (Recent card or list row) pins it to a separate Favorites list, opened from the sidebar. Kept apart from Recent so a favorite survives falling off the 20-item list; starring changes nothing on disk and is undone by starring again. Voice equivalents: "open favorites", "show recent files", "favorite recent", "favorite a file". Added after v1 scoping, at the developer's request.
- Remove from Recent: an icon-button on each Recent card in grid view (a row "⋯" menu item in list view), plus a voice equivalent, removes that entry from the list only — the underlying PDF file on disk is never touched, deleted, or renamed. Gated behind a confirmation dialog regardless of whether it was triggered by mouse or voice, and followed by a toast offering Undo. See the "Post-v1" section below for how this was scoped in.
- Find in document: Ctrl+F (or the toolbar's magnifier) opens a find bar that searches the whole document's text, marks every match, counts them ("3 of 17") and steps between them. A PDF with no text layer says so. Keyboard and mouse only for now; the voice equivalent, and with it the "Finding words" section of "What can I say?", is a Milestone 8 follow-up (`docs/TASKS.md` 8.14). Added after v1 scoping, at the developer's request. This whole-document search is separate from voice highlighting, which still only ever matches the visible viewport.
- Highlighting on scanned pages: a page that is a picture of text (no text layer) has its text read by offline OCR (English) when the reader first tries to highlight on it — by mouse or by voice — so both work there as on any other page. Per page, never per file (a PDF can mix scanned and ordinary pages), and never the whole document on open: one page at a time, on demand, with a brief "Reading text on this page…" while it happens. With voice on, a scanned page that stays on screen for about a second is read ahead, so a spoken highlight usually matches on the first try; when it is still being read, the reader is told to say it again. What was read is cached outside the PDF so a page is not read twice, and highlights are written into the PDF exactly as on a born-digital page. A page that cannot be read says so ("No text found on this page", "Couldn't read the text on this page") rather than doing nothing. Find in document still only searches pages with a text layer. Added after v1 scoping, at the developer's request; see `docs/TECH_STACK.md` and `docs/ARCHITECTURE.md`.
- Two reading layouts, user-toggleable: book (paginated, one page at a time) and continuous strip (scrolling, with a subtle page-break marker between pages).
- Reader layout, fixed (no placement setting): the toolbar on the right edge with the page's scrollbar just inside it; on the left edge a progress bar and a collapsible outline panel. The progress bar is a slim bar just inside the window's edge showing how far the reader is and a marker on every page with a highlight (a colour per theme that stays visible on the bar and the window, saved or not, following undo and redo); it is at full strength while the reader scrolls, turns pages or points near it, and fades back when left alone, the header's page number staying the main indicator; it is drawn by page, never by chapter: a pill per page when there is room (the current page's pill filling as the reader scrolls through it), one continuous bar when there is not; scrolled to the end of the document (or on the last page in Book) it is full; pointing at it widens it over the page with the current page number and a preview of the page under the pointer; clicking or dragging jumps there, and a page change by keyboard, voice or a jump briefly widens it to show where it landed. The outline panel opens beside it on Outline (the PDF's own bookmarks, nested, the current section marked) or Pages (thumbnails); a PDF without bookmarks opens on Pages (its Outline tab says so and offers the pages); the panel is 200px, resizable from 168 to 400px by its edge, with 128px page thumbnails (two columns once it is wide enough), and both its width and whether it is open are remembered; while it is open the progress bar stays a thin line, and pointing at it marks that page in the panel instead of showing a preview. Settings gains a Reading section: default view (book or strip, for PDFs opened for the first time), the highlight colour (the same active colour as the reader's), and the progress bar on or off. Voice: "show outline" and "show pages" (entries numbered, a spoken number jumps), "hide outline", "toggle progress bar". Added after v1 scoping, at the developer's request.
- Focus mode in the reader: F11, a button at the right end of the header, or "focus mode" hides the header, toolbar and footer together so the page has the window; Esc, F11, the same button or "exit focus mode" brings them back. Entering says how to leave in a brief toast, and pointing at the top edge of the window brings the header back over the page for as long as the pointer is on it. The progress bar and outline panel are unaffected, a small listening pill still shows while a command is being captured, and it is never remembered (every PDF opens with it off). Added after v1 scoping, at the developer's request.
- Zoom in the reader: 25–400%, where 100% is the page's real paper size (96 CSS px per inch, so A4 is 794 CSS px wide), drawn sharp for the screen's pixel density. − / + either side of the zoom value in the header (and Ctrl+= / Ctrl+-, Ctrl+scroll); clicking the value opens a small popover with a slider (marks at 50%, 100%, 200%; a drag near 100% settles there) and Fit width · Fit page · 100%. Fit width and Fit page keep the page fitted, with a margin, as the window, the outline panel or the layout changes, until a percentage is picked. Ctrl+0 / Ctrl+1 / Ctrl+2 are Fit page / 100% / Fit width, as in Acrobat, and "fit width", "fit page" and "actual size" are their voice commands. Resume reading restores the percentage, not a fit mode. Added after v1 scoping, at the developer's request.
- Full mouse/keyboard parity everywhere: voice is an accelerator on top of a fully usable traditional GUI, never a replacement for one. Every interactive element is a real, keyboard-focusable control.
- Discoverability: an on-screen "What can I say?" command reference, grouped into sections (Moving around / Highlighting / Finding words / The app itself, plus what applies on each screen), listing every phrase the recognizer accepts, for users unfamiliar with the exact command phrasing.
- Themes: light, dark, sepia.
- First-run onboarding: microphone permission request (skippable — app remains fully usable via mouse/keyboard if skipped) and voice activation mode selection (also changeable later in Settings).

## Post-v1: full in-app voice control

Every function of the app, once open, should be operable by voice — not just navigation and highlighting. App *launch* stays manual (the user opens Lector normally); voice control begins once the app is running, and closing the app is one of the voice commands. Requires: voice commands on Home and Settings (built in 8.5; 8.12 added the screen-wide ones — "open a PDF", "open settings", "go to Recent", "what can I say" — to all three screens, "open number N" on Home, and a spoken confirmation before voice can turn on "Overwrite the original"; voice can never switch voice activation off, so it cannot lock the reader out); a numbered-overlay picker for list items with no natural spoken name (e.g. a specific Recent card); in-app replacements for the native Open/Save-As file dialogs, since a native OS dialog can't be voice-driven; a dictation mode for free-text entry (never for a PDF's password, which is typed: a spoken one would pass through the recognizer, so the password dialog hears only "cancel"); and confirmation gating on any voice-triggered destructive action. Also adds one small new capability discovered while scoping this work: removing a file from the Recent list (list entry only — the underlying PDF is never touched), since a voice "remove"/"delete" command needs an existing feature to attach to and none existed. See `docs/TASKS.md` Milestone 8.1–8.12 and `docs/ARCHITECTURE.md`'s voice context router section.

## Post-v1: file tools

Added after v1 scoping, at the developer's request, in two tiers built in order: Tier 1 first, then Tier 2. Both are done with PyMuPDF and the Tesseract language data Lector already ships, so they add no library, no network use and no meaningful install size (see `docs/TECH_STACK.md`). Every tool works fully by mouse and keyboard; voice only opens a tool and then drives its dialog like any other dialog.

**Where they live.** In the reader, a More button (⋯) at the right end of the header, after Focus mode, opens a file menu: Save (Ctrl+S) and Save a copy… — which until now had no button, only a shortcut and a voice command — then the Tier 1 tools that act on the open PDF, and in Tier 2 Organise pages. On Home, a Tools item in the sidebar (between Favorites and Settings) opens a page listing every tool, and a Recent entry's ⋯ menu (in the list, and on each grid card) offers the tools that act on one PDF. A tool started from the Tools page asks for its file(s) through the in-app Open dialog. Nothing is added to the reader's toolbar rail, which stays for reading and marking.

**Rules every tool follows.**
- The original is never changed unless the reader chooses to. By default a tool writes a new file beside the original ("name (compressed).pdf", "name (searchable).pdf", a "name (images)" folder), through the same all-or-nothing write as Save, with its "Replace?" check and its skipping of taken names.
- Every tool that writes a file shows where it will go before it runs, and lets the reader change it: a Name field (the extension shown, not editable) and a "Save in" control showing the folder ("Reports — beside the original"). Clicking it lists Beside the original (the default every time, never remembered as a new default), up to three folders the reader picked recently (remembered across sessions), Desktop, Documents and Downloads, then "Choose another folder…", which opens the in-app folder picker (never a native dialog, so it stays voice-drivable). The result and the finished toast say where the file went ("Saved as … in Documents"), with Show in folder.
- A tool run from the reader uses the document as it is on screen, unsaved highlights included; the open document's own unsaved state is left as it was.
- Long jobs run off the interface's thread, show progress ("Page 34 of 120"; Compress shows its phases instead, since its image pass is one step) and can be cancelled; a cancelled job writes nothing. A running job can be sent to the background ("Keep reading"): it shows as a chip in the reader's footer and ends with a toast offering Open and Show in folder. One job at a time.
- A digitally signed PDF: the reader is told the new file won't carry the signature (the original keeps it). A password-protected PDF: the new file keeps the same protection (one exception, Combine files: see below).
- Failure messages follow Save's: what happened, in plain words, and that the original is unchanged.

**Tier 1**
- **Compress.** Three levels, chosen as option cards: Light (lossless: unused objects removed, streams recompressed, fonts subset; images untouched), Balanced (the default: images above 150 ppi resampled to 150, JPEG quality about 80) and Strong (images to 96 ppi, quality about 65). The dialog shows the current size; the result shows the new size and the saving. If the result isn't at least 5% smaller, no file is written and the reader is told the PDF is already compact. Highlights and other annotations are kept exactly, images are never enlarged, and an invisible text layer (from Make searchable) is kept.
- **Make searchable.** Adds an invisible text layer, read by the existing offline OCR (English), to the pages that have no text, so they can be found, selected and highlighted in any PDF viewer. The dialog says up front how many pages need it ("42 of 120 pages have no text"); pages with text are skipped; pages already read for highlighting reuse the OCR cache. The result lists any page where no text could be read. A PDF with no such pages says so instead of offering to run.
- **Export as images.** PNG or JPEG; 96, 150 or 300 ppi (the pixel size of the current page shown beside the choice); all pages, the current page or a range ("1–5, 8"). Written into a new "name (images)" folder beside the PDF as "name-p001.png" and so on. Highlights are drawn into the images.
- **Convert to PDF.** Images (PNG, JPEG, TIFF, BMP, GIF), EPUB, XPS, CBZ and FB2 to one PDF. Files are added one at a time with Add files…, or several at once by dropping them on the dialog. Several images become one PDF, one image a page, in an order the reader can change, at "Same as image" (the default), A4 or Letter page size. An EPUB's flowing layout is set out on A4 pages and comes out simpler than in an e-book reader, which the dialog says. Afterwards: Open in Lector, or Show in folder.

**Tier 2 (after Tier 1)**
- **Organise pages.** A grid of page thumbnails that takes over the reader's page area, to rotate (90° at a time), delete, reorder (drag, or Ctrl+←/→ on the selection), extract the selection to a new PDF, and insert pages from another PDF or from images. Selection works as in a file manager (click, Ctrl+click, Shift+click, Ctrl+A). While it is open, every action changes only a draft, with its own Undo and Redo. Two ways out: **Done** applies the draft to the open PDF as one change (the reader's Undo takes all of it back in one step, "Undo page changes"), and **Cancel** (or Esc) goes back to reading without changing the pages; with changes in the draft, Cancel first asks "Discard page changes?" (Keep editing, the default, or a red Discard changes). Closing the window or going back to the Library from Organise applies the draft first, then asks the usual "Save changes?" question. Applied changes are edits, like highlights: undoable, counted as unsaved changes and saved through the existing "Save changes?" flow; the PDF on disk doesn't change until it is saved. Delete (the toolbar button or the Delete key) always asks first, in a dialog that shows the selected pages' thumbnails and numbers, with Cancel as the default button and a red "Delete N pages" button; the deletion can still be undone afterwards. Deleting every page is refused before the dialog opens. Insert puts in all of the chosen file's pages, before or after the selection or at the end (only at the end when nothing is selected): a PDF (a protected one asks for its password, which is never stored), an image (one page per image, or per frame of a TIFF, at the image's own size), or an e-book Convert to PDF takes. Extract writes the selected pages, as the draft has them (turned, inserted pages and unsaved highlights included), to a new PDF through the file tools' destination block, protected as the original is; with "Also delete them from this PDF" ticked, the pages then leave the draft as one undoable step, with no further question.
- **Combine files.** Several PDFs (and images or e-books) into one, in an order the reader sets, from the Tools page; at least two files. Files are added with Add files… or by dropping them on the dialog. Annotations, links and form fields are kept; each file's bookmarks are kept, nested under a top-level bookmark named after the file (a file with none gets just that one, at its first page). A password-protected file asks for its password when added (never stored); the combined PDF is not protected, which the dialog and the result say, since the inputs' passwords can differ. A signed file: the new file won't carry signatures. Form fields from different files that share a name are kept but renamed by the PDF library, so the result names the files whose fields may not work. In Organise pages, Insert does the same into the open PDF.
- **Split.** One PDF per range, or one every N pages, from the Tools page; in Organise pages, Extract does it for the selection.

**Voice.** Kept small on purpose, since these are occasional jobs with choices to make: "compress this file", "make searchable", "export as images" and, in Tier 2, "organise pages" open the tool in the reader, and inside its dialog the existing dialog commands apply ("confirm", "cancel", numbered options). In Organise pages, "done" is the Done button and "cancel" the Cancel button. Formats, levels and page ranges are chosen by mouse or keyboard. All are listed in "What can I say?".

**Still out of scope.** Converting to or from Word, PowerPoint or Excel: it needs LibreOffice, Microsoft Office automation or a heavy layout library (pdf2docx pulls in OpenCV), against the lightweight goal, for results that are poor on complex layouts. Changing what is on a page (text, images) also stays out; every tool above works on whole pages or whole files.

## Explicitly out of scope for v1

- Full PDF editing: modifying text, repositioning images/tables, or any PDF↔Word round-trip conversion pipeline. Converting to or from any Office format (Word, PowerPoint, Excel) stays out too. Working on whole pages and whole files — compressing, making searchable, exporting as images, converting images and e-books to PDF, and rotating, deleting, reordering, extracting, inserting, combining and splitting pages — is in scope; see "Post-v1: file tools".
- General-purpose NLU / arbitrary phrasing comprehension. Voice commands use a fixed, synonym-mapped grammar (several known phrasings per intent), not open-ended speech understanding.
- Mobile app.
- Web app.

## Success criteria

The user can read a PDF for a full session hands-free, using only voice, without needing the mouse or keyboard for navigation or highlighting.

## Hard constraints

- **Budget:** $0 — no paid or cloud-based services of any kind.
- **Voice recognition must run fully offline** — privacy, zero marginal cost, and no internet dependency for the core reading use case.
- **Licensing:** MIT for original project code. The PySide6/Qt dependency is LGPL, so packaging must ship Qt as dynamically-linked shared libraries (not statically compiled into the executable) to remain compliant. (Not formal legal advice — standard defensible practice for this situation.)
- **Platform:** Windows + Mac desktop only for v1. No Linux, no mobile, no web.

## Naming

Mockups currently use "Lector" as a working name (it was auto-filled by the design-generation tool during iteration, not a deliberate choice yet). Not finalized — revisit before any public release or portfolio posting, including a basic trademark-conflict check.
