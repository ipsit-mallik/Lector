# Product Requirements Document

## Problem

Adobe Reader's ~10GB install footprint is unjustified for the actual use case: read-only PDF viewing, nothing else. Separately, hands are frequently occupied while reading (eating, exercising, chores), making mouse-driven scrolling, page navigation, and highlighting impractical.

## Who it's for

- **v1:** the developer, personal use.
- **Future (conditional):** public open-source release if there's demand, and a portfolio/social-media piece regardless of adoption.

## Must-have v1 features

- Voice-driven page navigation: next/previous page, jump to page N, scroll up/down.
- Speech-to-match highlighting: user speaks a few words, app fuzzy-matches them against the text currently visible in the viewport and highlights the matched span. Word-level matching is the baseline; sentence-level highlighting extends the match to the nearest sentence-ending punctuation (heuristic, not full sentence-segmentation NLP).
- Disambiguation rule when a phrase matches more than once: scope matching to the visible viewport only (never search the whole document); on a tie within the viewport, the first occurrence in reading order (top-to-bottom, left-to-right) wins.
- Real PDF annotation persistence via PyMuPDF — highlights are written as actual PDF annotation objects, so they're visible in any standard PDF viewer, not just this app.
- Highlight colours: a fixed set of five — yellow (the default), green, blue, pink, orange — and no free colour picker. The colour chosen next to the highlight tool is the active colour for every new highlight, by mouse or voice, and is an app-wide setting remembered across sessions. Clicking (or tabbing to) an existing highlight lets the reader change its colour or remove it; both are undoable like adding one. Voice: "highlight <words> in <colour>" colours one highlight without changing the active colour, and "highlight color <colour>" changes the active colour. Colours are written into the PDF annotation itself (its colour entry and its appearance), so other viewers show the same colour. Added after v1 scoping, at the developer's request. Recolouring or removing an *existing* highlight by voice is not included: it would need a way to name one highlight among several by speech, which no command does yet.
- Save-behavior preference: on the first explicit Save action, ask "Save a copy" vs. "Overwrite the original," with a "Don't ask again — remember this choice" checkbox (unchecked by default). The dialog is generalized to "Save changes?" — it is triggered only by an explicit Save action (voice command, click, or shortcut), never automatically as a side effect of highlighting or any other future edit. Saving is all or nothing: a failed or interrupted save never damages the original PDF or a file already at a copy's destination, and says in plain words what went wrong. "Save a copy" asks before replacing a file that already has the chosen name. A digitally signed PDF is never overwritten (that would break its signature); the reader is told to save a copy instead.
- Dual voice activation: push-to-talk (default key: Space) and a wake phrase ("Hey Lector"), independently toggleable; both remain available as fallback regardless of which is the default.
- Home screen "Recent" list: last 20 files, most-recent-first. With nothing in it, the empty state is the app's onboarding: a card with the Open PDF button, "or drop a file anywhere in this window", and a "TRY SAYING" row of example phrases (read from the voice command registry, never typed by hand).
- Drag-and-drop: dropping a PDF anywhere on the window opens it — from Home and Settings straight away, and from the reading view after the usual unsaved-highlights prompt. Anything that isn't a PDF is refused with a message. Added after v1 scoping, at the developer's request; the Open PDF button remains the equivalent for anyone not dragging.
- Resume reading: reopening a file from Recent returns the reader to the page, layout, and zoom level they left it on. Governed by a Settings preference ("Continue where I left off" — the default — vs. "Always start at the beginning"), so a reader who prefers every document to open at page 1 can have that. A document with no saved position — never opened before — always opens at the defaults (page 1, the default view from Settings > Reading — book unless changed — and 100% zoom), never with the previous document's view; "Always start at the beginning" uses the same defaults. Position is stored per document alongside its recent-files entry, so it is pruned automatically when the file falls off the 20-item list.
- Favorites: a star on each file (Recent card or list row) pins it to a separate Favorites list, opened from the sidebar. Kept apart from Recent so a favorite survives falling off the 20-item list; starring changes nothing on disk and is undone by starring again. Voice equivalents: "open favorites", "show recent files", "favorite recent", "favorite a file". Added after v1 scoping, at the developer's request.
- Remove from Recent: an icon-button on each Recent card in grid view (a row "⋯" menu item in list view), plus a voice equivalent, removes that entry from the list only — the underlying PDF file on disk is never touched, deleted, or renamed. Gated behind a confirmation dialog regardless of whether it was triggered by mouse or voice, and followed by a toast offering Undo. See the "Post-v1" section below for how this was scoped in.
- Find in document: Ctrl+F (or the toolbar's magnifier) opens a find bar that searches the whole document's text, marks every match, counts them ("3 of 17") and steps between them. A PDF with no text layer says so. Keyboard and mouse only for now; the voice equivalent, and with it the "Finding words" section of "What can I say?", is a Milestone 8 follow-up (`docs/TASKS.md` 8.14). Added after v1 scoping, at the developer's request. This whole-document search is separate from voice highlighting, which still only ever matches the visible viewport.
- Highlighting on scanned pages: a page that is a picture of text (no text layer) has its text read by offline OCR (English) when the reader first tries to highlight on it — by mouse or by voice — so both work there as on any other page. Per page, never per file (a PDF can mix scanned and ordinary pages), and never the whole document on open: one page at a time, on demand, with a brief "Reading text on this page…" while it happens. With voice on, a scanned page that stays on screen for about a second is read ahead, so a spoken highlight usually matches on the first try; when it is still being read, the reader is told to say it again. What was read is cached outside the PDF so a page is not read twice, and highlights are written into the PDF exactly as on a born-digital page. A page that cannot be read says so ("No text found on this page", "Couldn't read the text on this page") rather than doing nothing. Find in document still only searches pages with a text layer. Added after v1 scoping, at the developer's request; see `docs/TECH_STACK.md` and `docs/ARCHITECTURE.md`.
- Two reading layouts, user-toggleable: book (paginated, one page at a time) and continuous strip (scrolling, with a subtle page-break marker between pages).
- Reader layout, fixed (no placement setting): the toolbar on the right edge with the page's scrollbar just inside it; on the left edge a progress bar and a collapsible outline panel. The progress bar is a slim bar just inside the window's edge showing how far the reader is and a marker on every page with a highlight (a colour per theme that stays visible on the bar and the window, saved or not, following undo and redo); it is at full strength while the reader scrolls, turns pages or points near it, and fades back when left alone, the header's page number staying the main indicator; it is drawn by page, never by chapter: a pill per page when there is room (the current page's pill filling as the reader scrolls through it), one continuous bar when there is not; scrolled to the end of the document (or on the last page in Book) it is full; pointing at it widens it over the page with the current page number and a preview of the page under the pointer; clicking or dragging jumps there, and a page change by keyboard, voice or a jump briefly widens it to show where it landed. The outline panel opens beside it on Outline (the PDF's own bookmarks, nested, the current section marked) or Pages (thumbnails); a PDF without bookmarks opens on Pages (its Outline tab says so and offers the pages); the panel is 200px, resizable from 168 to 400px by its edge, with 128px page thumbnails (two columns once it is wide enough), and both its width and whether it is open are remembered; while it is open the progress bar stays a thin line, and pointing at it marks that page in the panel instead of showing a preview. Settings gains a Reading section: default view (book or strip, for PDFs opened for the first time), the highlight colour (the same active colour as the reader's), and the progress bar on or off. Voice: "show outline" and "show pages" (entries numbered, a spoken number jumps), "hide outline", "toggle progress bar". Added after v1 scoping, at the developer's request.
- Focus mode in the reader: F11, a button at the right end of the header, or "focus mode" hides the header, toolbar and footer together so the page has the window; Esc, F11, the same button or "exit focus mode" brings them back. Entering says how to leave in a brief toast, and pointing at the top edge of the window brings the header back over the page for as long as the pointer is on it. The progress bar and outline panel are unaffected, a small listening pill still shows while a command is being captured, and it is never remembered (every PDF opens with it off). Added after v1 scoping, at the developer's request.
- Zoom in the reader: 25–400%, where 100% is the page's real paper size (96 CSS px per inch, so A4 is 794 CSS px wide), drawn sharp for the screen's pixel density. − / + either side of the zoom value in the header (and Ctrl+= / Ctrl+-, Ctrl+scroll); clicking the value opens a small popover with a slider (marks at 50%, 100%, 200%; a drag near 100% settles there) and Fit width · Fit page · 100%. Fit width and Fit page keep the page fitted, with a margin, as the window, the outline panel or the layout changes, until a percentage is picked. Ctrl+0 / Ctrl+1 / Ctrl+2 are Fit page / 100% / Fit width, as in Acrobat, and "fit width", "fit page" and "actual size" are their voice commands. Resume reading restores the percentage, not a fit mode. Added after v1 scoping, at the developer's request.
- Full mouse/keyboard parity everywhere: voice is an accelerator on top of a fully usable traditional GUI, never a replacement for one. Every interactive element is a real, keyboard-focusable control.
- Discoverability: an on-screen "What can I say?" command reference, grouped into sections (Moving around / Highlighting / Finding words / The app itself, plus what applies on each screen), listing every phrase the recognizer accepts, for users unfamiliar with the exact command phrasing.
- Themes: light, dark, sepia.
- First-run onboarding: microphone permission request (skippable — app remains fully usable via mouse/keyboard if skipped) and voice activation mode selection (also changeable later in Settings).

## Post-v1: full in-app voice control

Every function of the app, once open, should be operable by voice — not just navigation and highlighting. App *launch* stays manual (the user opens Lector normally); voice control begins once the app is running, and closing the app is one of the voice commands. Requires: voice commands on Home and Settings (built in 8.5; 8.12 added the screen-wide ones — "open a PDF", "open settings", "go to Recent", "what can I say" — to all three screens, "open number N" on Home, and a spoken confirmation before voice can turn on "Overwrite the original"; voice can never switch voice activation off, so it cannot lock the reader out); a numbered-overlay picker for list items with no natural spoken name (e.g. a specific Recent card); in-app replacements for the native Open/Save-As file dialogs, since a native OS dialog can't be voice-driven; a dictation mode for free-text entry; and confirmation gating on any voice-triggered destructive action. Also adds one small new capability discovered while scoping this work: removing a file from the Recent list (list entry only — the underlying PDF is never touched), since a voice "remove"/"delete" command needs an existing feature to attach to and none existed. See `docs/TASKS.md` Milestone 8.1–8.12 and `docs/ARCHITECTURE.md`'s voice context router section.

## Explicitly out of scope for v1

- Full PDF editing: modifying text, repositioning images/tables, or any PDF↔Word round-trip conversion pipeline.
- General-purpose NLU / arbitrary phrasing comprehension. Voice commands use a fixed, synonym-mapped grammar (several known phrasings per intent), not open-ended speech understanding.
- Mobile app.
- Web app.

## Success criteria

The user can read a PDF for a full session hands-free, using only voice, without needing the mouse or keyboard for navigation or highlighting.

## Hard constraints

- **Budget:** $0 — no paid or cloud-based services of any kind.
- **Voice recognition must run fully offline** — privacy, zero marginal cost, and no internet dependency for the core reading use case.
- **Licensing:** MIT for original project code. The PySide6/Qt dependency is LGPL, so packaging must ship Qt as dynamically-linked shared libraries (not statically compiled into the executable) to remain compliant. (Not formal legal advice — standard defensible practice for this situation.)
- **Platform:** Windows + Mac desktop only for v1. No Linux, no mobile, no web.

## Naming

Mockups currently use "Lector" as a working name (it was auto-filled by the design-generation tool during iteration, not a deliberate choice yet). Not finalized — revisit before any public release or portfolio posting, including a basic trademark-conflict check.
